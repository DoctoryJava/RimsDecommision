B2 字段级加密实施指南

Databricks aes_encrypt() + Unity Catalog 列掩码 · 从建表到越权验证的完整最小示例
配套《企业级数据归档架构选型对比报告》第 6 章 L3 层 · 面向实施与评审
方案 B2 Databricks 读写一体 AES-256-GCM Unity Catalog 约 2~3 Man-day

零、先分清两件事 —— 这是最容易混淆的地方

很多人把「UC 列掩码」当成加密，其实它只管显示，不管落盘。

机制作用位置落盘状态防不防得住「绕过 UC 直读 Parquet」
UC 列掩码 查询返回时 明文 ✗ 防不住 —— 拿到存储凭据即得明文
aes_encrypt 写入时 密文 ✓ 防得住，但所有人查出来都是乱码
两者组合 ★ 写入加密 + 读时按角色解 密文 ✓ 防得住，且授权者查询体验正常
结论：隐私字段必须两者组合。单用列掩码有盲区——数据在 ADLS 上是明文 Parquet；单用 aes_encrypt 则所有人（含授权者）都要手工写解密语句。
本指南场景：customer 表的 name / idcard 两个隐私字段 ┌─ pii_reader 组 → 看到明文 张三 / 110101199001011234 ├─ 普通分析师 → 看到 *** └─ 绕过 UC 直读文件 → 看到密文 zK3mP9xQ2vN8fL1j... 同一条 SQL · 代码零改动 · 三种结果

实施步骤

六步 · 每步都可独立验证

0
准备密钥
一次性 · 管理员执行

先看清 secret() 的两个参数是什么——本指南中它们只是占位名，可以任意命名：

secret('archive-kv', 'dek')
        ↑            ↑
   Secret Scope 名   Key Vault 里那条 Secret 的键名
参数是什么谁定的
'archive-kv'Databricks Secret Scope 名——一个指向 Azure Key Vault 的「书签」，本身不存密钥值在 Databricks 创建 Scope 时自己起
'dek'Key Vault 里那条 Secret 的名字，密钥真身只存在这里在 Key Vault 创建 Secret 时自己起
Azure Key Vault: archive-kv-prod.vault.azure.net └── Secret 名: dek 值: <32 字符密钥> ← 密钥真身只在这里 └── Secret 名: dek-v2 值: <32 字符密钥> ↑ Scope 注册时绑定了这个 Vault 的 URI Databricks Secret Scope: "archive-kv" ← 只是引用，不存值 ↑ SQL: secret('archive-kv', 'dek') ← 运行时去 Key Vault 取
Scope 名与 Vault 名不必相同。Scope 是 Databricks 侧的别名，好处是切环境只改一个字符串：
secret('dev-kv','dek') / secret('prod-kv','dek') —— 同一份 SQL，只换 scope 名。

创建 Scope（一次性）：

databricks secrets create-scope --scope archive-kv \
  --scope-backend-type AZURE_KEYVAULT \
  --resource-id "/subscriptions/.../vaults/archive-kv-prod" \
  --dns-name "https://archive-kv-prod.vault.azure.net/"
⚠ 不要用 length() 验证密钥 —— 这个判断会误导你。
secret() 返回 STRING，length() 数的是字符数而非字节数。只有密钥存成纯 ASCII 时两者才相等：
Key Vault 里怎么存length() 返回实际密钥能否直接用
32 个 ASCII 字符（推荐）3232 字节✓ AES-256
32 字节二进制 → base64 存4432 字节✗ SQL 里须先 unbase64()
16 个 ASCII 字符1616 字节✓ AES-128
含中文的口令（3 汉字 + 29 ASCII）3238 字节✗ 长度非法，报错
建议：Key Vault 里直接存 32 个 ASCII 字符（字母数字），最省事。
若安全规范要求存真随机二进制，就 base64 存，SQL 写成 aes_encrypt(col, unbase64(secret(...)))——加密与解密两侧必须一致，一边加了 unbase64 另一边没加就解不开。

正确的验证方式：做一次加解密往返

SELECT CAST(
  try_aes_decrypt(
    aes_encrypt('test-value', secret('archive-kv','dek')),
    secret('archive-kv','dek')
  ) AS STRING) AS roundtrip;

-- 返回 'test-value' → 密钥可取到、长度合法 ✓
-- 返回 NULL 或报错   → 密钥长度不对（必须 16/24/32 字节）
这一条同时验证了「能取到密钥」和「密钥长度合法」两件事，比数长度可靠。
普通用户跑这条应该失败——那正是我们要的效果，第 6 步会专门验证。
1
建表
密文列用 STRING 存 base64
CREATE TABLE archive.sys01.customer (
  id      BIGINT,
  name    STRING COMMENT '密文·base64',
  idcard  STRING COMMENT '密文·base64',
  city    STRING                        -- 非隐私字段，不加密
);

只对真正的隐私字段加密。非隐私字段保持明文，才能正常参与 WHERE / GROUP BY / JOIN。

2
写入时加密
ETL 阶段 · 有一个会静默损坏数据的坑
⚠ 高危：不要把 secret() 内联在 INSERT / UPDATE 语句里。
Databricks 有一道安全机制，会把输出中「看起来像凭据」的字符串替换成 REDACTED。而 aes_encrypt 产生的 base64 密文有概率恰好命中 40 字符的 AWS Access Key 特征，于是被替换成 REDACTED_POSSIBLE_SECRET_ACCESS_KEY —— 并且真的写进表里。
后果：那一行数据永久损坏、再也解不开，而且全程不报错。这是 Databricks 社区已确认的实际案例，官方支持给出的规避方式是——先把密钥取到变量，再用 expr() 拼进去。

✓ 推荐写法：密钥先落变量

# 1) 先取密钥到变量（不在写入语句内部调 secret）
key = dbutils.secrets.get("archive-kv", "dek")

# 2) 再用 expr() 拼进加密表达式
(df
  .withColumn("name",   expr(f"base64(aes_encrypt(name,   '{key}'))"))
  .withColumn("idcard", expr(f"base64(aes_encrypt(idcard, '{key}'))"))
  .write.mode("append").saveAsTable("archive.sys01.customer"))

✗ 有风险的写法：secret() 内联在写入语句中

INSERT INTO archive.sys01.customer VALUES
  (1, base64(aes_encrypt('张三', secret('archive-kv','dek'))), ..., '北京');
--                                     ↑ 可能触发 redaction 损坏密文
注意适用范围：这个坑只影响「写入」。第 3 步掩码函数里的 secret() 属于读取路径，不受影响，可以保持原样。

此刻先验证落盘状态（这一步很多人跳过）：

-- 此时还没挂掩码，管理员可直接看原始列
 id | idcard                                        | city
----+-----------------------------------------------+------
  1 | zK3mP9xQ2vN8fL1jR7wY5tA0sD4gH6bC1eU3iO9pW2==  | 北京
  2 | mB5nT8kX3zV6qJ9wL2yF7cR4dG1hS0aE8uI5oP3rN6==  | 上海
✓ 密文确认。就算有人绕过 UC 直接读 ADLS 上的 Parquet 文件，拿到的也是这串东西。
3
建掩码函数
整套机制的核心
CREATE OR REPLACE FUNCTION archive.gov.unmask_pii(col STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('pii_reader')
    THEN CAST(try_aes_decrypt(unbase64(col), secret('archive-kv','dek')) AS STRING)
  ELSE '***'
END;
写法为什么必须这样
try_aes_decrypt
而非 aes_decrypt		 前者失败返回 NULL，后者抛异常导致整个查询挂掉。表里混有历史明文或旧密钥数据时能救命。
is_account_group_member 它以调用者身份求值，而函数体其余部分以定义者身份运行——这就是安全闭环的来源。
CAST(… AS STRING) aes_decrypt 返回 BINARY，必须显式转回 STRING，否则前端拿到的是字节数组。
4
挂到列上
一个函数可复用到多列
ALTER TABLE archive.sys01.customer ALTER COLUMN name   SET MASK archive.gov.unmask_pii;
ALTER TABLE archive.sys01.customer ALTER COLUMN idcard SET MASK archive.gov.unmask_pii;

不用为每个字段写一遍函数。若不同字段要不同遮蔽规则（如手机号保留后四位），再另建函数即可。

6
越权测试
上线前必做

用普通分析师账号跑这两条，都必须失败：

-- 测试① 直接取密钥 → 应报无权限
SELECT secret('archive-kv','dek');

-- 测试② 自己解密 → 拿不到 key，解不开
SELECT aes_decrypt(unbase64(idcard), secret('archive-kv','dek'))
FROM archive.sys01.customer;
⚠ 如果测试①成功了，整套防线归零。说明业务用户被误授了 Secret Scope 的 READ 权限——他可以自己写解密语句绕过掩码。
这是唯一能让本机制完全失效的配置错误，必须验。

一、为什么这样是安全的 —— definer's rights 机制

UC 函数的权限模型恰好构成闭环

掩码函数 unmask_pii() ← 整体以【定义者权限】运行 │ ├─ secret('archive-kv','dek') → 能读到密钥（定义者有权限）✓ │ └─ is_account_group_member('...') → 但这个函数【以调用者身份】求值 ✓ 判断的是真实发起查询的人 普通分析师的三条路，全部走不通： · 对 Secret Scope 无权限 → 自己调 secret() 拿不到密钥 · 只有函数的 EXECUTE 权限 → 通过函数读，返回的是 '***' · 自己写 aes_decrypt(col, ???) → 没有 key，解不开
关键点：密钥始终没有离开过 Databricks 的执行引擎，也从未下发到客户端或前端。用户拿到的永远只是函数的返回值，而返回什么由引擎根据其组身份决定。

二、分组的常见做法

避免一个组通吃全部系统

-- 按「系统 + 敏感级」组合授权，审计员单独一个组跨系统
CREATE OR REPLACE FUNCTION archive.gov.unmask_pii_sys01(col STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('pii_reader_sys01') THEN CAST(try_aes_decrypt(...) AS STRING)
  WHEN is_account_group_member('auditor')          THEN CAST(try_aes_decrypt(...) AS STRING)
  ELSE '***'
END;

审计员通常需要跨系统查看，单独给一个组比逐系统加人省事得多。15 个系统的话，就是 15 个 pii_reader_sysNN + 1 个 auditor。

三、密钥轮换 —— 一条 DDL，历史数据一行不动

对照方案 A 的复杂度，差距最明显的地方

-- 1. Key Vault 里放新版本密钥 → Secret Scope 指向新版本
-- 2. 改函数，新旧双解
CREATE OR REPLACE FUNCTION archive.gov.unmask_pii(col STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('pii_reader') THEN
    COALESCE(
      CAST(try_aes_decrypt(unbase64(col), secret('archive-kv','dek-v2')) AS STRING),
      CAST(try_aes_decrypt(unbase64(col), secret('archive-kv','dek-v1')) AS STRING)
    )
  ELSE '***'
END;
原理：新密文用 v2 能解开；老密文 v2 解不开返回 NULL，COALESCE 自动回落到 v1。历史数据一行都不用重刷。

密钥轮换自研版本前缀解析 + DEK 分片调度 + 进度台账 + 双读逻辑改一条 DDL
盲索引必须自建，且会泄露频率分布不需要

谁来保证自研代码，漏写一个接口就是一个泄露点引擎强制，绕过应用直连也拦得住

建设差额约 ¥1.5~2.2 万不算大，真正的差距是持续维护与能力完整度——A 那套要一直养着，B2 就是几条 DDL。

四、三条运维红线

每一条都会让机制失效或造成故障

  • 绝不能改成 ECB 模式。aes_encrypt 默认 GCM（每次随机 IV）。改成 ECB 后相同明文产生相同密文，频率分布直接暴露——对低基数字段（性别、状态标记）几乎等同明文，而且连盲索引那种「截断制造碰撞」的缓解手段都用不上。保持默认即可。
  • 掩码不支持视图（View）。必须打在基表上。若配置化查询平台走了视图层，掩码会静默失效——不报错，就是查出明文，极难在测试中发现。
  • 删除顺序不能反。必须先 DROP MASK 再 DROP FUNCTION，反了表会进入不可访问状态。
-- ✗ 错误：掩码还挂着就删函数 → 表不可访问
DROP FUNCTION archive.gov.unmask_pii;

-- ✓ 正确顺序
ALTER TABLE archive.sys01.customer ALTER COLUMN idcard DROP MASK;
DROP FUNCTION archive.gov.unmask_pii;
另需注意运行环境：读取带掩码的表要求 SQL Warehouse，或 DBR 12.2 LTS+（标准访问模式）；专用访问模式需 15.4 LTS+ 读、16.3+ 写。老版本集群读不了掩码表。

五、必须向上说明的代价

这套机制完全绑定 Unity Catalog。
数据本身不会被锁住——密文是标准 AES-GCM，任何语言、任何引擎只要有密钥都能解开，Iceberg 也是开放格式。
被锁住的是治理逻辑：掩码策略、角色判断、审计链路，换引擎需要全部重做。

补充：若改用 Trino 读，UC 列掩码完全不可用。Databricks 官方明确——带 row filter 或 column mask 的表不能通过 Iceberg REST catalog 访问，且是 fail closed（直接报错，不会静默泄露）。这也正是本项成为 B2 相对 B 的独有优势的原因。
