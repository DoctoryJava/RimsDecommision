1结论

核心认知 AKS 提供的是基础设施的高可用（控制平面 SLA、节点自动修复），不提供应用的高可用。应用高可用 = 冗余（活着的副本）× 流量正确性（不把流量打给要死的 Pod）× 调度可行性（被赶走的 Pod 有地方去）。三者缺一，节点升级就是一次事故。

2背景：什么会打断业务（为什么要按这个优先级改）

最高频场景：节点池滚动升级

drain node（节点封锁） ↓ evict pods（按 Eviction API 驱逐，受 PDB 约束） ↓ 重新调度到新节点（需要有容量承接）

控制平面升级不影响 Pod 运行（仅 API Server 短暂抖动）；节点池滚动升级必然触发驱逐。此时应用如果存在以下短板，中断就是必然的：

应用状态结果对应整改项
单副本❌ 必然中断⑥ replicas ≥ 2
没有 readinessProbe / 优雅下线❌ 摘流失败，请求打到将死 Pod④⑦
没有 PDB / PDB 配错❌ 被一次性全部驱逐 或 升级卡死①②③
节点资源不足❌ 驱逐后调度失败，直接 downtime⑤⑫
使用本地存储（hostPath/emptyDir）❌ Pod 迁移 = 数据丢失⑯
ℹ️ 一句话本质 业务中断 = Pod 被驱逐 + 没有冗余承接。所有整改项都在消除这个等式的一侧。

1

PDB 统一改用 maxUnavailable，禁止 minAvailable 与 HPA 组合

后果等级：节点池升级超时失败（确定性）｜成本：10 分钟/服务

问题机制：minAvailable 是绝对值。HPA 低峰缩容到下限时（如 minReplicas: 2 + minAvailable: 2），disruptionsAllowed 恒为 0 → drain 永久阻塞 → 节点池升级卡住直至超时。现象极具误导性：升级失败，但所有 Pod 都 Running、健康检查全绿。这是 AKS 节点池升级失败最常见的单一原因。

统一规则（三条）

规则说明
① 只要配了 HPA，一律用 maxUnavailablemaxUnavailable 是相对值，随副本数自动伸缩，官方文档亦推荐。无 HPA 的服务也统一用 maxUnavailable 保持一致
② 副本数波动大的服务可用百分比HPA 从 3 扩到 10 的服务用 maxUnavailable: "25%"（3 副本允许 1 个、10 副本允许 3 个）。百分比向上取整，不会锁死驱逐。⚠️ 百分比只在 maxUnavailable 上安全，minAvailable: "90%" 小副本时取整后等于副本数、照样死锁
③ 若遗留系统必须保留 minAvailable则 HPA 的 minReplicas 必须严格大于 minAvailable，且两值任何一方变更时必须联动评审——因此仍强烈建议直接迁移到 maxUnavailable，让该约束自动消失
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: my-service-pdb
spec:
  maxUnavailable: 1                         # 固定小副本用整数；HPA 波动大用 "25%"
  unhealthyPodEvictionPolicy: AlwaysAllow   # 1.27+，防不健康 Pod 反向阻塞运维
  selector:
    matchLabels:
      app: my-service                       # 必须与 Pod 实际标签完全一致

PDB 基础语义（团队须知）

字段语义注意
spec.minAvailable任何时候至少要有 X 个 Pod 存活不能 ≥ replicas（否则锁死）；本方案原则上弃用
spec.maxUnavailable同一时间最多允许 X 个 Pod 不可用本方案统一采用；两字段二选一，不能同时存在
status.disruptionsAllowed当前还能安全驱逐几个 Pod> 0 ✅ 可安全驱逐；= 0 ❌ drain 被阻止

PDB 不是绑定 Deployment 的，是通过 selector 绑定 Pod 的——这就是 selector 命中问题（整改项 3）存在的原因。

后果等级：升级阻塞元凶｜成本：一条命令排查 + 逐个修复

kubectl get pdb -A -o custom-columns=`
'NS:.metadata.namespace,NAME:.metadata.name,MIN:.spec.minAvailable,MAXUNAVAIL:.spec.maxUnavailable,ALLOWED:.status.disruptionsAllowed,CURRENT:.status.currentHealthy'

稳态下 ALLOWED 必须 ≥ 1。为 0 的常见原因及处理：

原因处理
minAvailable = 当前副本数（含 HPA 缩容所致）改 maxUnavailable（整改项 1）
maxUnavailable: 0 / minAvailable: 100%等于禁止一切驱逐，删除或改为 1

3

修正 PDB selector 命中问题 / 单副本与重叠 PDB

后果等级：保护形同虚设 或 反向锁死｜成本：脚本自动检出
  • selector 必须与 Pod 标签一致：PDB 创建成功不代表命中。验收标准：status.currentHealthy == 实际副本数
  • 单副本服务不配 PDB：单副本 + 任何限制性 PDB = 永久锁死节点驱逐（CA 也无法缩容）。单副本要么接受中断，要么先扩到 2 副本
  • 禁止多个 PDB 命中同一组 Pod：Eviction 会直接失败（不是取最严格的），必须去重

4P1核心必改 — 不改就升级掉请求（随下次发版全量带上）

4

优雅下线：preStop + terminationGracePeriodSeconds + 应用处理 SIGTERM

后果等级：升级/发版必现 502（对外服务）｜成本：YAML 两行 + 应用侧配置

问题机制——Pod 被删除的瞬间，两条路径并行发生、没有顺序保证：

┌─ 路径1（同步、快）: kubelet 收到删除 → 立刻发 SIGTERM → 进程开始退出 DELETE └─ 路径2（异步、慢）: EndpointSlice 摘除 → kube-proxy / Ingress 更新规则 ← 需 1~10 秒！

进程已退出但流量还在进来 → 502 / Connection Reset。节点升级批量驱逐时被放大为错误率尖刺。readinessProbe 管不了这个场景（Pod 删除时探针即停止执行），必须用 preStop 等待摘除传播完成：

spec:
  template:
    spec:
      terminationGracePeriodSeconds: 45      # 必须 > preStop + 存量请求处理时间
      containers:
        - name: app
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 15"]   # 期间进程仍正常服务
  • sleep 时长：AKS + Application Gateway/AGIC 场景 15~30s；纯 ClusterIP 场景 5~10s
  • distroless 镜像无 shell → 用 httpGet 型 preStop 或应用内 SIGTERM handler
  • 应用侧配套：SIGTERM 后停止接新连接、处理完存量请求再退出（Spring Boot server.shutdown=graceful；.NET IHostApplicationLifetime；Nginx nginx -s quit）
  • 长连接/gRPC/WebSocket：sleep 不会断开已有连接，需应用发 GOAWAY / 主动关闭空闲连接，grace 时间相应加长

范围界定：对外 HTTP/API 服务为强制项；内部有重试机制的异步/消费类服务为建议项。

5

resources.requests 全量补齐（memory.limits == requests）

后果等级：驱逐后 Pending / 节点压力时被优先杀 / HPA 指标失真｜成本：按 P95 用量测算

为什么是地基：① 不设 requests，调度器认为 Pod 不占资源 → 节点超卖 → 被驱逐的 Pod 无处落位（PDB 保得了驱逐节奏、保不了"驱逐后起不来"）；② QoS 决定驱逐顺序：BestEffort → Burstable → Guaranteed，这类驱逐不走 Eviction API、PDB 无效；③ HPA 的 averageUtilization 是相对 requests 的百分比——requests 不准，HPA 就是错的。

resources:
  requests: { cpu: 200m, memory: 512Mi }    # 必填，按 P95 实际用量
  limits:
    memory: 512Mi          # == requests：内存不可压缩，避免 OOMKill 抽奖
    cpu: 1000m             # CPU limit 可放宽；延迟敏感服务警惕 CFS throttling

核心业务≥ 3
有状态服务（仲裁集群）≥ 3，取奇数（3/5）
⚠️ 真实案例 CA072：配置 ≠ 结果 replicas = 2 ✅、集群 2 个 Node ✅、配了 podAntiAffinity (preferred) ✅ —— 结果 Pod 还是全在一个 Node 上 ❌。原因：preferred 是打分阶段的软偏好，会被镜像本地性、资源余量等其他打分插件稀释，两副本落同一节点完全合法。教训有二：① 必须用 kubectl get pod -o wide 验证实际分布（Anti-Affinity 是"关系偏好"，topologySpread 才是"结果约束"，见整改项 ⑨）；② 2 节点集群本身就是容量瓶颈——任一节点升级 = 50% 容量损失且无第三节点承接，配置解决不了容量问题（见整改项 ⑫）。
7

readinessProbe 规范化

后果等级：流量打给未就绪 Pod｜成本：低（多数服务已有，重点是查漏 + 校准）
readinessProbe:
  httpGet: { path: /health/ready, port: 8080 }
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3        # 摘流要快

端点必须真实反映"能否处理请求"（依赖初始化完成、连接池就绪），不能只返回 200。

8

livenessProbe 禁止检查任何外部依赖

后果等级：级联雪崩（一旦发生为全局性事故）｜成本：规范约束，逐步排查
🔥 雪崩场景 liveness 检查数据库 → DB 抖动 10 秒 → 所有副本、所有服务的 liveness 同时失败 → 全部重启 → DB 恢复后被冷启动流量再次打挂。比原本的 DB 抖动严重得多。
探针应检查绝对不能检查
readinessProbe自身能否处理请求；可选检查强依赖—
livenessProbe仅进程自身存活（纯内存判断）❌ DB / Redis / 下游 API

liveness 本身定为可选：配错的 liveness 比没有 liveness 危害更大。配置时 failureThreshold 要比 readiness 宽松得多（重启要慢，摘流要快）。

5P2生产标准 — 1~2 个迭代内补齐

9

topologySpreadConstraints（hostname 级为主，AZ 集群加 zone 级）

解决：副本挤在同一节点的假冗余（P1-⑥ 验证不通过时的修复手段）

反亲和 preferred 是"关系偏好"，topologySpread 是"结果约束"——它不选择跑哪台机器，而是控制"Pod 在机器之间怎么分布"（Node / AZ 等拓扑维度的均匀程度）。标准模板两者并用（模板见第 7 节）；追求精简可只保留 topologySpread。

配置位置固定：写在 Pod Template 里（spec.template.spec.topologySpreadConstraints），与 containers、affinity、resources 同级；labelSelector 必须与 Pod 标签一致。

whenUnsatisfiable行为适用
ScheduleAnyway尽力均匀，不满足也调度（软）默认，安全
DoNotSchedule不满足则 Pending（硬）核心服务；节点数 < replicas 时会卡发版，先确认容量

zone 级约束的前提是集群真的启用了 AZ：先 kubectl get nodes -L topology.kubernetes.io/zone 确认，未启用则不配（纯摆设）。

10

发版策略：rollingUpdate.maxUnavailable: 0 + minReadySeconds

解决：发版期间容量塌陷 —— PDB 对发版不生效，发版由 rollingUpdate 管
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0      # 先起新的再停旧的，发版零容量损失
    maxSurge: 1
minReadySeconds: 10        # 新 Pod Ready 后再观察 10s，防"起来就崩"雪崩式发版
progressDeadlineSeconds: 600

对外服务强制；内部服务默认值可接受。maxUnavailable: 0 需要 maxSurge 份额外容量 → 关联整改项 ⑫。

11

HPA 规范化

解决：峰值扛不住 / 反复扩缩抖动 / GitOps 与 HPA 抢副本数
  • minReplicas ≥ 2（建议与基线 replicas 一致）；maxReplicas 按业务峰值设定 + Cluster Autoscaler 承接，用 ResourceQuota 兜成本
  • 配置 behavior：scaleDown 稳定窗口 600s 防抖动，scaleUp 放开应对突发
  • 启用 HPA 后，Helm/GitOps 不再管理 spec.replicas：否则每次同步与 HPA 抢控制权造成副本抖动。Helm 用 {{- if not .Values.autoscaling.enabled }} 条件渲染，ArgoCD 对该字段 ignoreDifferences
  • 定位澄清：HPA 是容量弹性方案，不是高可用方案——它解决"扛不扛得住"，不解决"挂不挂"
  • 配了 HPA 必须同时有 PDB：HPA 只管副本数量，管不了驱逐节奏，两者是配套关系（PDB 用 maxUnavailable 即天然兼容，见整改项 ①）
ℹ️ 怎么知道一个服务有没有 HPA Deployment 从来不感知 HPA——HPA 是"外部控制器"，看 Deployment YAML 是看不出来的，只能 kubectl get hpa。会产生 HPA 的三种来源：Helm Chart 包含 HPA、CI/CD 中 apply 了 HPA、kubectl autoscale 命令。审计时必须以集群实际状态为准（第 9 节脚本已按 scaleTargetRef 自动关联）。
11+

节点调度约束使用规范（nodeSelector / nodeAffinity）

解决：调度僵化——AKS 节点本来就会随升级频繁重建变化
选项态度原因
nodeSelector❌ 禁止硬匹配，节点标签变化即调度失败
nodeAffinity: preferred✅ 推荐软偏好，节点不满足时仍可调度
nodeAffinity: required⚠️ 仅特殊场景与 nodeSelector 同等僵化，节点不够即 Pending
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
            - key: agentpool
              operator: In
              values: ["pool-a"]
12

集群容量 N+1（节点 ≥3 + 一个节点的空闲余量）

解决：驱逐/发版时 Pod 无处落位 —— 配置解决不了容量问题

Node 数量至关重要，它决定了上层所有配置能发挥的上限：

集群规模可行做法说明
单 Nodereplicas 1~3，不配置 PDB无冗余可言，配 PDB 只会锁死升级；仅限开发/测试
2 Nodereplicas 3 + maxUnavailable: 1勉强可用但脆弱：任一节点升级 = 50% 容量损失、无第三节点承接（CA072 的根因）
3 Node（生产推荐）replicas 3 + maxUnavailable: 1 + topologySpread 每节点 1 个 Pod升级时始终 2 副本在线且有落位空间，是生产最低标准

在此之上保持 ≥1 节点的空闲容量（N+1），配合多 Node pool 与 Cluster Autoscaler 从平台侧兜底。属于预算决策，需平台侧与管理层确认。

13

startupProbe（限慢启动应用）

解决：Java/.NET 冷启动 60~120s 被 liveness 误杀 → CrashLoopBackOff 死循环
startupProbe:
  httpGet: { path: /health/live, port: 8080 }
  periodSeconds: 5
  failureThreshold: 30       # 允许 150s 启动窗口；配置后 readiness/liveness 不再需要 initialDelaySeconds

只对启动 > 30s 的应用配置，其余服务不需要。

14

LimitRange 兜底（配合整改项 ⑤）

防止新服务漏配 requests，在每个业务 namespace 设置默认值；有条件的用 Gatekeeper/Kyverno 强制。

6P3成熟度建设 — 季度规划，防止配置退化

#整改项要点
15PriorityClass核心 1000000 / 一般 100000 / 批处理 0；资源紧张时保核心服务不被日志采集、测试负载挤掉
16跨 AZ 与存储Azure Disk 是 zonal 资源：PVC 绑定 AZ-1 后 Pod 永远无法调度到 AZ-2。有状态服务 StorageClass 必须 WaitForFirstConsumer；跨 AZ 共享用 Azure Files / ZRS 盘；禁用 hostPath/emptyDir 存持久数据。注意 AZ 只能在 node pool 创建时启用
17平台组件自身 HACoreDNS（≥2 副本 + 反亲和 + proportional autoscaler）、Ingress Controller / AGIC、metrics-server（挂了 HPA 全停）——业务 Pod 全配齐、Ingress 单副本照样全站中断。平台组件按同一标准（多副本 + PDB + 分散）配置
18节点池 maxSurge默认值小（1 或 10%），生产建议 --max-surge 33%：升级更快，新节点先就绪、被驱逐 Pod 有落点；同时设置计划维护窗口，把自动升级固定到业务低峰
19监控告警核心规则：disruptions_allowed == 0 持续 15 分钟（最高价值，预警升级阻塞）；PDB currentHealthy == 0（selector 打空）；available replicas < 2；Pod Pending > 5 分钟；同 Deployment Pod 集中单节点
20季度 drain 演练非生产先行：① drain 单节点观察错误率（一次性暴露 P0/P1 所有问题）② 删单个 Pod 验证 preStop ③ 关停一个 AZ 验证容灾 ④ 完整节点池升级记录耗时与错误率。配置正确 ≠ 高可用生效，没有演练闭环的方案只是纸面方案

9全集群审计脚本（PowerShell，摸底 + 验收共用）

单脚本一次性输出全维度：探针 / preStop / requests / 分布约束 / 发版策略 / PDB 有效性与死锁检测 / HPA / Pod 实际落点，按 P1~P3 风险分级，可导出 CSV。

# ============================================================
# AKS 应用高可用审计 —— 全维度单脚本版
# 用法: .\Audit-AksHa.ps1 -Namespaces @("wiki","cdp","default")
#       .\Audit-AksHa.ps1 -AllNamespaces -CsvPath report.csv
# ============================================================
param(
  [string[]]$Namespaces,
  [switch]$AllNamespaces,
  [string]$CsvPath
)

if ($AllNamespaces) {
  $Namespaces = kubectl get ns -o json | ConvertFrom-Json |
    Select-Object -ExpandProperty items |
    ForEach-Object { $_.metadata.name } |
    Where-Object { $_ -notin @("kube-system","kube-public","kube-node-lease","gatekeeper-system") }
}
if (-not $Namespaces) { Write-Error "请指定 -Namespaces 或 -AllNamespaces"; return }

# --- 预取全集群 PDB / HPA / Pod，避免逐 namespace 反复调用 ---
$allPdb  = kubectl get pdb  -A -o json | ConvertFrom-Json | Select-Object -ExpandProperty items
$allHpa  = kubectl get hpa  -A -o json | ConvertFrom-Json | Select-Object -ExpandProperty items
$allPods = kubectl get pods -A -o json | ConvertFrom-Json | Select-Object -ExpandProperty items

function Test-SelectorMatch($selector, $podLabels) {
  if (-not $selector -or -not $selector.matchLabels) { return $false }
  foreach ($k in $selector.matchLabels.PSObject.Properties.Name) {
    if ($podLabels.$k -ne $selector.matchLabels.$k) { return $false }
  }
  return $true
}

$report = foreach ($ns in $Namespaces) {

  $workloads = kubectl get deploy,sts -n $ns -o json 2>$null |
    ConvertFrom-Json | Select-Object -ExpandProperty items -ErrorAction SilentlyContinue
  if (-not $workloads) { continue }

  foreach ($w in $workloads) {
    $name = $w.metadata.name
    $kind = $w.kind
    $pspec = $w.spec.template.spec
    $podLabels = $w.spec.template.metadata.labels
    $containers = $pspec.containers
    $replicas = [int]$w.spec.replicas
    $ready = [int]$w.status.readyReplicas

    $hasReadiness = [bool]($containers | Where-Object { $_.readinessProbe })
    $hasStartup   = [bool]($containers | Where-Object { $_.startupProbe })
    $hasLiveness  = [bool]($containers | Where-Object { $_.livenessProbe })
    $hasPreStop   = [bool]($containers | Where-Object { $_.lifecycle.preStop })
    $grace        = $pspec.terminationGracePeriodSeconds

    $missingReq = @($containers | Where-Object {
        -not $_.resources.requests.cpu -and -not $_.resources.requests.memory
      }).Count
    $hasRequests = ($missingReq -eq 0)

    $aff = $pspec.affinity
    $hasAntiAff  = [bool]($aff -and $aff.podAntiAffinity)
    $hasNodeSel  = [bool]$pspec.nodeSelector
    $spreadKeys  = @($pspec.topologySpreadConstraints | ForEach-Object { $_.topologyKey })
    $hasSpreadHost = $spreadKeys -contains "kubernetes.io/hostname"
    $hasSpreadZone = $spreadKeys -contains "topology.kubernetes.io/zone"

    $rollingMaxUnavail = if ($kind -eq "Deployment") {
      "$($w.spec.strategy.rollingUpdate.maxUnavailable)"
    } else { "n/a" }

    # PDB：按 selector 实际匹配，而非靠命名猜测
    $pdb = $allPdb | Where-Object {
      $_.metadata.namespace -eq $ns -and (Test-SelectorMatch $_.spec.selector $podLabels)
    }
    $pdbCount = @($pdb).Count
    if ($pdbCount -ge 1) {
      $p = @($pdb)[0]
      $pdbName    = $p.metadata.name
      $pdbPolicy  = if ($null -ne $p.spec.maxUnavailable) { "maxUnavailable=$($p.spec.maxUnavailable)" }
                    else { "minAvailable=$($p.spec.minAvailable)" }
      $pdbAllowed = $p.status.disruptionsAllowed
      $pdbHealthy = $p.status.currentHealthy
    } else {
      $pdbName = "-"; $pdbPolicy = "-"; $pdbAllowed = "-"; $pdbHealthy = "-"
    }

    $hpa = $allHpa | Where-Object {
      $_.metadata.namespace -eq $ns -and
      $_.spec.scaleTargetRef.name -eq $name -and
      $_.spec.scaleTargetRef.kind -eq $kind
    }
    if ($hpa) {
      $h = @($hpa)[0]
      $hpaRange = "$($h.spec.minReplicas)-$($h.spec.maxReplicas)"
      $hpaMin = [int]$h.spec.minReplicas
    } else { $hpaRange = "-"; $hpaMin = 0 }

    # Pod 实际分布（验证分散是否真的生效）
    $myPods = $allPods | Where-Object {
      $_.metadata.namespace -eq $ns -and
      $_.metadata.ownerReferences -and
      (Test-SelectorMatch $w.spec.selector $_.metadata.labels)
    }
    $nodes = @($myPods | ForEach-Object { $_.spec.nodeName } | Sort-Object -Unique)
    $nodeSpread = "$($nodes.Count)N/$(@($myPods).Count)P"

    # ---------- 风险判定 ----------
    $risks = [System.Collections.Generic.List[string]]::new()
    if ($replicas -lt 2)                       { $risks.Add("P1:单副本") }
    if (-not $hasReadiness)                    { $risks.Add("P1:无readiness") }
    if (-not $hasPreStop -and $replicas -ge 2) { $risks.Add("P1:无preStop") }
    if (-not $hasRequests)                     { $risks.Add("P1:无requests") }
    if ($pdbPolicy -like "minAvailable*" -and $hpaRange -ne "-") {
      $risks.Add("P0:PDB-HPA死锁风险")
    }
    if ($pdbAllowed -eq 0)                     { $risks.Add("P0:disruptions=0阻塞升级") }
    if ($pdbCount -gt 1)                       { $risks.Add("P0:多PDB重叠") }
    if ($replicas -lt 2 -and $pdbCount -ge 1)  { $risks.Add("P0:单副本配PDB") }
    if ($replicas -ge 2 -and $pdbCount -eq 0)  { $risks.Add("P2:无PDB") }
    if ($replicas -ge 2 -and -not $hasSpreadHost -and -not $hasAntiAff) {
      $risks.Add("P2:无分布约束")
    }
    if ($replicas -ge 2 -and $nodes.Count -eq 1) { $risks.Add("P2:Pod集中单节点") }
    if ($kind -eq "Deployment" -and $rollingMaxUnavail -notin @("0","0%")) {
      $risks.Add("P3:rollingUpdate非0")
    }
    if ($hpaRange -ne "-" -and $hpaMin -lt 2)  { $risks.Add("P2:HPA下限<2") }
    if ($hasNodeSel)                           { $risks.Add("P3:用了nodeSelector") }
    if ($hasLiveness -and -not $hasStartup)    { $risks.Add("P3:有liveness无startup") }
    if ($ready -lt $replicas)                  { $risks.Add("P2:副本未就绪") }

    [PSCustomObject]@{
      NS            = $ns
      NAME          = $name
      KIND          = $kind
      REPLICAS      = $replicas
      READY         = $ready
      NodeSpread    = $nodeSpread
      Readiness     = if ($hasReadiness) {"Y"} else {"N"}
      Startup       = if ($hasStartup)   {"Y"} else {"N"}
      Liveness      = if ($hasLiveness)  {"Y"} else {"N"}
      PreStop       = if ($hasPreStop)   {"Y"} else {"N"}
      Grace         = $grace
      Requests      = if ($hasRequests)  {"Y"} else {"N"}
      SpreadHost    = if ($hasSpreadHost){"Y"} else {"N"}
      SpreadZone    = if ($hasSpreadZone){"Y"} else {"N"}
      AntiAff       = if ($hasAntiAff)   {"Y"} else {"N"}
      NodeSel       = if ($hasNodeSel)   {"Y"} else {"N"}
      RollingMaxUnav= $rollingMaxUnavail
      PDB           = $pdbName
      PDBPolicy     = $pdbPolicy
      PDBAllowed    = $pdbAllowed
      PDBHealthy    = $pdbHealthy
      HPA           = $hpaRange
      RiskLevel     = if ($risks -match "P0") {"P0"}
                      elseif ($risks -match "P1") {"P1"}
                      elseif ($risks -match "P2") {"P2"}
                      elseif ($risks.Count) {"P3"} else {"OK"}
      Risks         = ($risks -join "; ")
    }
  }
}

# ---------- 输出 ----------
Write-Host "`n===== 阻塞升级（P0）=====" -ForegroundColor Magenta
$report | Where-Object RiskLevel -eq "P0" |
  Select-Object NS,NAME,KIND,PDBPolicy,PDBAllowed,HPA,Risks | Format-Table -AutoSize -Wrap

Write-Host "`n===== 高危（P1）=====" -ForegroundColor Red
$report | Where-Object RiskLevel -eq "P1" |
  Select-Object NS,NAME,KIND,REPLICAS,NodeSpread,Risks | Format-Table -AutoSize -Wrap

Write-Host "`n===== 需改进（P2）=====" -ForegroundColor Yellow
$report | Where-Object RiskLevel -eq "P2" |
  Select-Object NS,NAME,REPLICAS,NodeSpread,Risks | Format-Table -AutoSize -Wrap

Write-Host "`n===== 全量明细 =====" -ForegroundColor Cyan
$report | Sort-Object RiskLevel,NS,NAME |
  Select-Object NS,NAME,KIND,REPLICAS,READY,NodeSpread,
                Readiness,PreStop,Requests,SpreadHost,
                PDBPolicy,PDBAllowed,HPA,RiskLevel | Format-Table -AutoSize

Write-Host "`n===== 汇总 =====" -ForegroundColor Green
$report | Group-Object RiskLevel |
  Select-Object @{n="Level";e={$_.Name}}, Count | Sort-Object Level | Format-Table -AutoSize
Write-Host "工作负载总数: $($report.Count)"

if ($CsvPath) {
  $report | Export-Csv -Path $CsvPath -NoTypeInformation -Encoding UTF8
  Write-Host "已导出: $CsvPath" -ForegroundColor Green
}

10验收 Checklist

P0 升级不失败（当天）

  • 所有 PDB 使用 maxUnavailable（有 HPA 时禁用 minAvailable）
  • 稳态下所有 PDB 的 disruptionsAllowed ≥ 1
  • PDB selector 命中验证：currentHealthy == 实际副本数
  • 单副本服务未配 PDB；无多 PDB 命中同一组 Pod

P1 升级不掉请求（随发版）

  • 对外服务全部配置 preStop + terminationGracePeriodSeconds，应用处理 SIGTERM
  • 所有容器有 resources.requests；memory.limits == memory.requests
  • replicas ≥ 2（核心 ≥3），并用 -o wide 验证实际分散在不同节点
  • readinessProbe 已配置且真实反映服务状态
  • livenessProbe 不检查任何外部依赖（或不配）

P2 生产标准（1~2 迭代）

  • topologySpreadConstraints（hostname 级）已配置；启用 AZ 的集群加 zone 级
  • 对外服务 rollingUpdate.maxUnavailable: 0 + minReadySeconds ≥ 10
  • HPA minReplicas ≥ 2 + behavior.scaleDown 稳定窗口；GitOps 不再管理 replicas
  • 集群节点 ≥3 且有 N+1 空闲容量
  • 慢启动应用配置 startupProbe；namespace 有 LimitRange 兜底

P3 成熟度（季度）

  • 核心服务设置 priorityClassName；不使用 nodeSelector，nodeAffinity 仅用 preferred
  • 有状态服务 StorageClass 为 WaitForFirstConsumer；无持久数据写 hostPath/emptyDir
  • CoreDNS / Ingress Controller / metrics-server 多副本 + PDB
  • 节点池 maxSurge 已调优 + 计划维护窗口已设置
  • disruptionsAllowed == 0 等核心告警已上线
  • 每季度 drain 演练并记录错误率
