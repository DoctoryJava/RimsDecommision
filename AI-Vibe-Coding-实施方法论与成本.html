01

总览：流程形状变了

传统流程是串行的瀑布：需求文档 → 架构设计 → 编码 → 测试 → 交付，每个阶段产出"给人看的文档"，编码占掉一半人力。AI 模式不是把其中一步加速，而是改变了流程的形状：规格直接驱动生成、测试先于编码、架构约束从文档变成每次会话强制注入的规则。

对比两种形状：传统是"单向流水线"（需求→架构→编码→测试→交付），错了回头代价大；AI Vibe 是"规格冻结后的高频小循环"——架构被前置固化进宪法文件，测试嵌进生成循环，错误在会话内就被拦截，而不是流到测试阶段才暴露。

02

逐阶段对比：五个阶段，五种本质变化

每个阶段一句话说清：传统怎么做 → AI 怎么做 → 关键差别，都用本项目举例。

阶段一 · 需求

TRADITIONAL传统：写给人看

  • 几十页 Word 规格书，靠人读、靠人脑补歧义
  • 需求说得含糊（"要脱敏"），具体怎么做等开发自己猜
  • 验收标准到最后测试阶段才被翻出来

AI VIBEAI：写给机器执行

  • 写成验收语句（Given-When-Then），机器能直接判对错
  • 每条需求量到可验证（"无权限角色查询 → 返回掩码 + 记录审计"）
  • 验收语句直接当测试用例——需求即测试靶子
RIMS 场景传统写法AI 模式写法
脱敏需求"客户姓名等敏感信息需要脱敏后展示，具体规则由开发与安全协商确定"「Given 表 CUSTOMER_ORDER 含 isPii 字段 customer_name When 无脱敏权限的角色查询 Then 返回 MASK_FIRST_N(4) 掩码且 sys_audit_log 记录查询者/时间/表名」
附件安全"附件下载链接需要有时效性，避免泄露"「Given 用户请求附件预览 When RBAC 校验通过 Then 签发 SAS URL 且 有效期 ≤15 分钟，过期访问返回 403」
查询性能"查询响应要快，大数据量下不能超时"「归档查询走 Statement Execution API，30s 超时，默认 LIMIT 100、上限 10000，超限提示收敛条件」
销毁合规"数据到期后需要销毁，销毁前要确认"「Given 系统状态 EXPIRING When 管理员单方点击销毁 Then 系统拒绝——必须第二管理员确认（双人制）后才执行 DROP+VACUUM，全程审计」
关键差别：传统需求"给人看"，人可以脑补歧义；AI 需求"给机器看"，歧义 = 生成错误。把需求写到 AI 能执行的精度，恰好也是传统测试最想要的精度——AI 逼着需求变好。本项目 task.csv 已有 113 条任务骨架，缺的是把每条升级为验收语句。

阶段二 · 架构

TRADITIONAL传统：画完就归档

  • 架构师出白皮书 + 评审，周期 2~4 周
  • 评审通过后文档吃灰，靠人记住约束，久了规范就走样
  • 新人进来、时间一长，没人再按文档执行

AI VIBEAI：写进宪法，强制读取

  • 架构 = 项目宪法（AGENTS.md），每次 AI 会话自动读取
  • 约束从"靠人记住"变成"机器生成前必读"——不会忘、不会走样
  • 重大决策一页 ADR（背景/选项/结论），AI 可检索复用
RIMS 宪法条款内容（POC 的 AGENTS.md 已有雏形）强制机制（传统模式做不到的）
七条 Do NOTPOC 已存在 ✓不改 V1/V2 迁移、不绕过 DynamicQueryBuilder 白名单、不在 JS/Java 做脱敏、MySQL 不存业务数据等写入 AGENTS.md，每次会话注入；再升级为 CI 规则（ArchUnit + gitleaks）机器强制
分层边界controller→service→mapper 单向依赖；前端 decommission/ 不跨界 importArchUnit / ESLint import 规则，违反即 CI 失败
引擎抽象生产新增SyncEngine / QueryEngine 接口：生产 Databricks、演示 SeaTunnel+Spark 双实现可切换接口稳定性测试 + ADR-001 记录决策理由
状态机封闭REGISTERED→CONFIGURED→SYNCING→ARCHIVED→EXPIRING→DESTROYED，跳转只经状态机服务非法跳转单测即失败；销毁跳转额外要求双人确认
关键差别：传统架构文档是"交付物"，写完就吃灰；AI 架构是"生产资料"，每次生成都被读取并约束输出。架构师从"画图的人"变成"立法的人"。本项目 AGENTS.md 的七条禁令在 12 天 167 次提交中自发有效，就是因为规则写进了会话上下文。

阶段三 · 编码

TRADITIONAL传统：人逐行写

  • 工程师手写 Controller / Mapper / 前端，估多少人就排多少人
  • 速度随人数线性涨，靠开会对齐
  • 质量靠 code review 兜底，一次审一整块功能

AI VIBEAI：会话循环生成

  • 任务拆到"一个会话一个任务一个分支"
  • AI 生成 → 自动跑测试/lint/build → 失败自修 → 全绿才交人审
  • 只读任务可并行，写码任务串行避免冲突；人的产出 = 审查通过的合并量
三个代表性生成任务：① SAS 签发服务——宪法规定"前端永不持有 Access Key"，AI 在此约束下生成带 15min 过期 + 审计的 BlobSasService；② DynamicQueryBuilder——白名单 + 参数化 SQL 是宪法条款，AI 的拼接尝试会被 lint 打回；③ 动态查询前端——schema_json 直接驱动动态渲染，新系统接入零代码。

阶段四 · 测试

TRADITIONAL传统：写完再测

  • 开发写完提测，测试组再写用例、报 bug、回归
  • 覆盖率在交付压力下常被牺牲
  • 安全测试（脱敏/越权）往往拖到上线前才抽查
  • 缺陷发现越晚，修复成本越高（晚一步贵 5~10 倍）

AI VIBEAI：测试先行

  • 测试先于实现：验收语句直接变 BDD 用例，当 AI 的生成靶子
  • 退出标准 = 测试全绿，"看着对"不算，可验证才算
  • AI 批量生成常规用例；人只盯三类：安全、不可逆（销毁）、跨边界
用例类型谁写RIMS 例子为什么这么分
功能用例AI 生成Schema CRUD、分页查询、RBAC 判断逻辑的正反用例数量大、模式化，AI 生成效率是人写的 10 倍级
安全用例人写 · 人审无脱敏权限查询 isPii 字段必须见掩码；SAS 过期后 403；越权访问他系统数据被拒合规红线，AI"自我测试"不可信——生成者不能当裁判
不可逆用例人写 · 人审销毁双人确认缺一不可；DESTROYED 后任何查询/恢复路径都失败错了无法回滚，必须穷尽边界
回归用例AI 维护引擎切换后（Databricks ↔ SeaTunnel+Spark）同一套 BDD 全绿接口双实现的契约测试，AI 比人勤快

阶段五 · 交付验收

TRADITIONAL传统：人工点页面

  • UAT = 业务方按清单人工点页面，2~4 周
  • 审计举证靠翻日志 + 截图拼材料
  • 移交：代码 + 文档 + 培训
  • "这段代码为什么这么写"——三个月后没人说得清

AI VIBEAI：全量机械回放

  • UAT = BDD 用例在准生产环境全量回放，绿 = 通过
  • 审计演练脚本化：脱敏对照、SAS 过期、"谁查了什么"一键导出
  • 移交多三样：宪法 + ADR + 会话档案，"为什么这么写"可追溯
03

AI 模式的六个步骤（本项目工作流）

把第 02 章的差异落成可执行流程。六个步骤覆盖从需求到验收的完整链路，每步标注主导者（人 / AI）并给出 RIMS 实例。这就是"传统五阶段"在 AI 模式下的实际形态——注意测试不再是独立阶段，而是嵌进步骤④的循环里。

需求结构化

人主导
把口语需求写成"AI 能执行"的验收语句（Given-When-Then），并把性能指标量化定稿。这一步的质量，决定后面所有步骤的速度。

Spec 冻结

人审批
把验收语句汇编成 spec 文件，连同项目宪法（禁令 + 红线 + 边界）一起评审冻结。冻结后改需求必须走变更流程，不许"边生成边改"。

任务拆解

AI 拆 · 人核
把 spec 拆成"一个会话一个任务一个分支"，每个任务都有明确验收命令。只读任务可并行，写码任务串行。

会话生成

AI 执行
AI 读宪法 → 生成代码 → 自动跑测试 → 失败自修复 → 全绿才停。验证不过会话不许结束，AI 必须出示测试证据。

审查合并

人审查 · 不可绕过
人只聚焦三类 diff 逐行审：安全敏感、不可逆（销毁/DDL）、跨边界（引擎/状态机），其余页面样式快速扫过合并。

验收回放

AI 回放 · 人签字
里程碑/UAT 不用人工点页面：BDD 用例在准生产环境全量机械回放，绿 = 通过，人签字验收。同时跑审计演练并归档度量与会话档案。
六步 vs 传统五阶段：需求结构化 + Spec 冻结 ≈ 传统"需求+架构"；任务拆解 + 会话生成 ≈ 传统"编码"（人从写代码变成管会话）；审查合并 + 验收回放 ≈ 传统"测试+交付"（但测试已前置嵌进生成循环）。总人天 290 → 159（-45%），重心从编码移到规格——详见第 05 章。

3.1 六步骤的工具化：用 GitHub Spec Kit 跑同一套流程

六步骤不需要自建工具链。GitHub 官方开源的 Spec Kit（github/spec-kit · 129.6k star · MIT · 2026-08 核实）把"先定义要建什么，再动手建"的规格驱动开发（SDD）做成了现成 CLI，与 30+ AI 编码代理兼容（Claude Code / Copilot / Codex / Gemini CLI 等，含本仓库在用的 pi 类工具）。其核心主张：规格不再是写完即弃的脚手架，而是可执行的——直接驱动实现生成。安装两条命令即得与六步骤同构的流水线：

安装与初始化uv tool install specify-cli
specify init rims-decommission --integration copilot  # integration 可换 claude / codex / gemini 等 30+ 代理
Spec Kit 命令干什么对应六步骤在 RIMS 怎么用
/speckit.constitution建立项目治理原则，此后每个生成步骤强制遵守STEP 2把 AGENTS.md 七条 Do NOT + 三条红线 + 分层边界 + 状态机规则写入 constitution.md
/speckit.specify生成需求与用户故事——只写 what/why，不写技术栈STEP 1四条 Epic（登记→同步→查询→销毁）各生成一份 spec.md；验收语句内含
/speckit.clarify可选 · plan 前跑AI 就模糊点反向提问，逼出歧义STEP 1"SAS 有效期几分钟？""销毁需几人确认？""LIMIT 上限多少？"——正补 NFR 量化表
/speckit.plan技术实现计划——这一步才引入技术栈STEP 2引擎抽象（SyncEngine/QueryEngine）、UC 治理、Flyway V19+ 平移策略
/speckit.tasks从 plan 生成可执行任务清单STEP 3生成 60~80 张会话级任务卡；/speckit.taskstoissues 可直接转 GitHub Issues 跟踪
/speckit.analyze可选 · implement 前spec ↔ plan ↔ tasks 跨工件一致性与覆盖率核查护栏 L4规格冻结前跑一遍，防 spec 自相矛盾或任务漏覆盖（官方称之"给英文写的单元测试"）
/speckit.implement按任务清单逐项执行实现STEP 4每个任务在验证循环内跑到全绿（配合第 04 章 Stop hook 门禁）
/speckit.converge★ 存量库专用评估现有代码库与目标 spec 的差距，剩余工作自动转为新任务POC→生产本项目最关键的一条：拿生产 spec 对照 POC 代码库，自动生成"重建任务清单"——Phase B 的工作来源

WHY FIT对 RIMS 的三个加分点

  • converge 匹配 POC 场景：RIMS 是典型的"存量库演进"（Brownfield）——官方三阶段（新建/探索/迭代增强）中明确支持此形态，POC 代码不必推倒，差距自动转任务
  • Presets 支持合规定制：可强制 spec 模板带监管可追溯性、给 plan 加安全审查门——正好承载等保/审计要求
  • Bundles 角色包：PM / 业务分析 / 安全研究员 / 开发者各有一键配置，3.5 人团队按角色取用

BOUNDARY它不覆盖什么（诚实边界）

  • STEP 5 人工审查：三类 diff 强制人审是制度（CODEOWNERS + 分支保护），Spec Kit 不管
  • STEP 6 验收回放：BDD 全量回放需自建测试基建，Spec Kit 只负责到任务执行
  • 七层护栏：jscpd 重复度、gitleaks、ArchUnit 等仍需第 04 章的 CI 配置——工具给流程骨架，护栏要自己立法
采用结论：六步骤中 STEP 1–4 直接用 Spec Kit 命令驱动（不自建流程脚手架），STEP 5–6 与七层护栏由本项目的 CI 制度承接——工具负责流程骨架，制度负责质量底线，两者合起来才是完整的交付轨。第 05 章路线图 Phase A 已将 specify init 纳入首个交付动作。
04

人机分工与质量护栏

原则一句话：AI 负责 Draft（草稿），人负责 Decision（决策）与 Guard（护栏）。凡不可逆、涉密、触碰红线的，人守 A（最终负责）。

4.1 RACI 矩阵（A=最终负责 R=执行 C=咨询 I=知会）

业务目标与优先级A + RI人的领地，AI 只知会
验收语句（GWT）AR人定边界与量化指标，AI 展开为完整语句并追问歧义

安全用例（脱敏/越权/审计）A + RC生成者不能当裁判：AI 的代码由 AI 测试不可信
销毁链路（不可逆）A + RC双人确认制度本身也是人写人审
