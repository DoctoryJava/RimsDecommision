01

总览：流程形状变了

传统流程是串行的瀑布：需求文档 → 架构设计 → 编码 → 测试 → 交付，每个阶段产出"给人看的文档"，编码占掉一半人力。AI 模式不是把其中一步加速，而是改变了流程的形状：规格直接驱动生成、测试先于编码、架构约束从文档变成每次会话强制注入的规则。

传统流程（线性 · 文档驱动 · 人写代码）
需求调研Word 规格书 · 给人看
架构设计白皮书 · 评审后归档
编码人逐行写 · 占 50% 人力
测试编码后补 · 常被压缩
交付验收人工点页面 · UAT
AI Vibe 流程（规格驱动 · 测试先行 · 循环生成）
① 需求结构化验收语句 · 给 AI 执行
② Spec 冻结spec.md + 项目宪法
③ 任务拆解拆到"一个会话一个任务"
④ 会话生成生成→验证→修复循环
⑤ 审查合并 + ⑥ 验收回放人审三类 diff · BDD 重跑
注意形状差异：传统是"单向流水线"，错了回头代价大；AI 模式是"规格冻结后的高频小循环"——每个任务都走「生成 → 自动验证 → 不绿不停 → 人审 → 合并」，错误在会话内就被拦截，而不是流到测试阶段才暴露。架构设计没有消失，而是前置固化进步骤②的宪法文件，每次生成都被强制读取。

02

逐阶段对比：五个阶段，五种本质变化

每个阶段回答三个问题：传统怎么做？AI 模式怎么做？用本项目的真实场景举例。

阶段一 · 需求：从"写给人看的文档"到"写给 AI 执行的验收语句"

TRADITIONAL传统做法

  • 产出 SRS 规格书（几十页 Word），面向人阅读
  • 需求描述依赖自然语言，留大量解释空间："敏感字段需要脱敏展示"
  • 变更走需求变更单，文档更新滞后于实际
  • 验收标准写在 Excel 清单里，测试阶段才被翻出来

AI VIBEAI 模式

  • 产出验收语句（Given-When-Then），面向机器执行，人审批
  • 需求必须量化到可判真假，否则 AI 无法生成达标代码
  • NFR（性能/安全指标）与功能需求同等结构化
  • 验收语句直接成为测试用例——需求即测试靶子
RIMS 场景传统写法AI 模式写法
脱敏需求"客户姓名等敏感信息需要脱敏后展示，具体规则由开发与安全协商确定"「Given 表 CUSTOMER_ORDER 含 isPii 字段 customer_name When 无脱敏权限的角色查询 Then 返回 MASK_FIRST_N(4) 掩码且 sys_audit_log 记录查询者/时间/表名」
附件安全"附件下载链接需要有时效性，避免泄露"「Given 用户请求附件预览 When RBAC 校验通过 Then 签发 SAS URL 且 有效期 ≤15 分钟，过期访问返回 403」
查询性能"查询响应要快，大数据量下不能超时"「归档查询走 Statement Execution API，30s 超时，默认 LIMIT 100、上限 10000，超限提示收敛条件」
销毁合规"数据到期后需要销毁，销毁前要确认"「Given 系统状态 EXPIRING When 管理员单方点击销毁 Then 系统拒绝——必须第二管理员确认（双人制）后才执行 DROP+VACUUM，全程审计」
本质变化：传统需求文档的读者是开发工程师（人可以脑补歧义）；AI 模式的读者是生成引擎（歧义 = 生成错误）。把需求写到"AI 能执行"的精度，恰好也是传统模式下测试与验收最想要的那种精度——AI 逼着需求变好。本项目现有的 task.csv（113 条任务清单）和 README 四阶段业务流已具备骨架，缺的是把每条升级为验收语句。

阶段二 · 架构：从"设计白皮书"到"会话强制注入的项目宪法"

TRADITIONAL传统做法

  • 架构师出白皮书 + 评审会，周期 2~4 周
  • 评审通过后文档归档，靠开发者记忆和 code review 维持约束
  • 技术选型靠调研报告（本项目如：PG vs 湖仓、Appsmith vs 自研——见《归档架构选型对比报告》）
  • 架构约束失效是常态：新人加入、时间一长，规范悄悄走样

AI VIBEAI 模式

  • 架构 = 项目宪法文件（AGENTS.md 升级版），每次 AI 会话自动强制读取
  • 约束从"靠人记住"变成"机器每次生成前必读"——不会忘、不会走样
  • POC 即架构参照物：选型已在 POC 验证（SeaTunnel 入湖 → Iceberg → Spark 查询已跑通），生产只需补 ADR 决策记录
  • 重大决策一页 ADR（背景/选项/结论），AI 可检索复用
RIMS 宪法条款内容（POC 的 AGENTS.md 已有雏形）强制机制（传统模式做不到的）
七条 Do NOTPOC 已存在 ✓不改 V1/V2 迁移、不绕过 DynamicQueryBuilder 白名单、不在 JS/Java 做脱敏、MySQL 不存业务数据等写入 AGENTS.md，每次会话注入；再升级为 CI 规则（ArchUnit + gitleaks）机器强制
分层边界controller→service→mapper 单向依赖；前端 decommission/ 不跨界 importArchUnit / ESLint import 规则，违反即 CI 失败
引擎抽象生产新增SyncEngine / QueryEngine 接口：生产 Databricks、演示 SeaTunnel+Spark 双实现可切换接口稳定性测试 + ADR-001 记录决策理由
状态机封闭REGISTERED→CONFIGURED→SYNCING→ARCHIVED→EXPIRING→DESTROYED，跳转只经状态机服务非法跳转单测即失败；销毁跳转额外要求双人确认
本质变化：传统架构文档是"交付物"（写完归档落灰），AI 模式的架构是"生产资料"（每次生成都被读取并约束输出）。本项目 AGENTS.md 的七条禁令在 POC 阶段已自发证明有效——12 天 167 次提交没有出现"绕过白名单拼 SQL"这类违规，就是因为规则写进了会话上下文。架构师的角色从"画图的人"变成"立法的人"。

阶段三 · 编码：从"人逐行写"到"会话编排 + 生成验证循环"

TRADITIONAL传统做法

  • 工程师逐行编写：Controller/Service/Mapper/前端页面，估 3 人月的活就排 3 人月
  • 速度与人数线性相关；并行开发靠模块分工 + 频繁开会对齐
  • 代码质量靠 code review 兜底，review 粒度是"整个功能"
  • 本项目的量：20 Controller + 22 Service/Mapper + 22 实体 + 16 前端页面

AI VIBEAI 模式

  • 任务拆到"一个会话一个任务一个分支"（如"实现 BlobSasService"是一个会话）
  • 每个会话内：AI 生成 → 自动跑 mvn test / lint / build → 失败自动修复 → 全绿才交人审
  • 只读任务（调研/评审/用例生成）多会话并行；写码任务单会话串行避免冲突
  • 人的产出 = 审查通过的合并量；POC 实证此节奏：日均 14 次提交
本项目最有代表性的三个生成任务（生产阶段同粒度拆解）：① SAS 签发服务——宪法规定"前端永不持有 Access Key"，AI 在此约束下生成 BlobSasService + 15min 过期 + 路径前缀校验 + 审计埋点；② DynamicQueryBuilder——白名单 + 参数化 SQL 是宪法条款，AI 生成的任何拼接尝试都会被 lint 规则打回；③ 动态查询前端——Schema Registry 的 schema_json 直接驱动 DynamicFilterForm/DynamicDataTable 渲染，新系统接入零代码，这正是 AI 生成模式与元数据驱动架构的乘数效应。

阶段四 · 测试：从"事后补写"到"先行的生成靶子"

TRADITIONAL传统做法

  • 开发提测后，测试组写用例、执行、报 bug、回归
  • 单元测试靠开发自觉，覆盖率常在交付压力下妥协
  • 安全测试（脱敏/越权/审计）往往只在上线前抽查
  • 缺陷发现越晚，修复成本越高（测试阶段发现的成本 ≈ 编码阶段的 5~10 倍）

AI VIBEAI 模式

  • 测试先于实现：阶段一的验收语句直接转为 BDD 用例，作为 AI 的生成靶子
  • AI 循环的标准退出条件 = 测试全绿，"看起来对"不算完成，可验证才算
  • AI 批量生成常规用例；人只聚焦三类高价值用例：安全（脱敏/越权）、不可逆（销毁）、跨边界（引擎切换）
  • 缺陷在会话内暴露（分钟级），不再流到测试阶段
用例类型谁写RIMS 例子为什么这么分
功能用例AI 生成Schema CRUD、分页查询、RBAC 判断逻辑的正反用例数量大、模式化，AI 生成效率是人写的 10 倍级
安全用例人写 · 人审无脱敏权限查询 isPii 字段必须见掩码；SAS 过期后 403；越权访问他系统数据被拒合规红线，AI"自我测试"不可信——生成者不能当裁判
不可逆用例人写 · 人审销毁双人确认缺一不可；DESTROYED 后任何查询/恢复路径都失败错了无法回滚，必须穷尽边界
回归用例AI 维护引擎切换后（Databricks ↔ SeaTunnel+Spark）同一套 BDD 全绿接口双实现的契约测试，AI 比人勤快

阶段五 · 交付验收：从"人工点页面"到"BDD 全量回放"

TRADITIONAL传统做法

  • UAT = 业务方按验收清单人工点页面，周期 2~4 周
  • 审计举证靠翻日志 + 截图拼材料
  • 移交物：代码 + 文档 + 培训
  • "这段代码为什么这么写"——三个月后没人说得清

AI VIBEAI 模式

  • UAT = 阶段一的 BDD 用例在准生产环境全量机械回放，绿 = 通过
  • 审计演练脚本化：脱敏对照查询、SAS 过期验证、"谁在何时查了什么"一键导出
  • 移交物多三样：宪法 + ADR 集 + 会话档案（167 次提交对应完整生成过程记录）
  • "为什么这么写"→ 回放会话档案与 ADR，可追溯
03

AI 模式的六个步骤（本项目工作流）

把第 02 章的差异落成可执行流程。六个步骤覆盖从需求到验收的完整链路，每步标注主导者（人 / AI）并给出 RIMS 实例。这就是"传统五阶段"在 AI 模式下的实际形态——注意测试不再是独立阶段，而是嵌进步骤④的循环里。

需求结构化：把需求写成验收语句

人主导 · AI 辅助展开
人定业务边界与量化指标，AI 把口语需求展开为完整 Given-When-Then 语句并主动追问遗漏（"销毁确认是单人还是双人？""SAS 有效期多少分钟？"）。
  • 输入：README 四阶段业务流、task.csv 113 条任务、访谈记录
  • 关键动作：NFR 量化表定稿（30s 超时 / LIMIT 10000 / SAS≤15min / 覆盖率≥70%）
RIMS 实例 · 产出片段「Given 退役系统含 100 张表，When 管理员配置 Schema Registry 并确认，Then 每张表生成 schema_json 描述符且 isPii/objectKeyField 字段完成标注；未标注 isPii 的表不得进入同步阶段」
产出：Epic 级验收语句集 + NFR 量化表 —— 这一步的质量决定后面所有步骤的速度

Spec 冻结：spec.md + 项目宪法

人审批 · AI 起草
AI 把验收语句汇编为结构化 spec 文件（每条 Epic 一份），连同项目宪法（AGENTS.md 升级版：七条禁令 + 三条红线 + 分层边界 + 状态机规则）一并提交评审。人批准后冻结——此后任何修改走变更流程，不许"边生成边改需求"。
  • 三条红线：销毁双人确认 / 密钥永不明文 / 脱敏必须平台侧（UC COLUMN MASK）
  • Schema Registry 的 schema_json 升级为规格附件（字段级验收已内含）
RIMS 实例 · 宪法条款"Do NOT 在 JS/Java 层实现字段脱敏——isPii 列只允许 UC COLUMN MASK（MASK_FULL / MASK_FIRST_N）；任何应用层'等效脱敏'的实现一律拒绝合并。"（POC 的 mask.ts 前端脱敏即为此条款要替换的对象）
产出：冻结版 spec.md × 4 + constitution（宪法）+ ADR 补录 5~8 条

任务拆解：拆到"一个会话一个任务"

AI 拆解 · 人校验粒度
AI 按 spec 生成任务清单（tasks.md），每个任务满足：一个分支、一次会话可完成、有明确验收命令（如 `mvn test -Dtest=BlobSasServiceTest`）。人只校验粒度与依赖顺序。
  • 依赖排序示例：先 DDL（Flyway V19+）→ 再引擎接口 → 再服务实现 → 最后前端页面
  • 并行判据：只读任务（契约比对/用例生成/文档）多会话并行；写码任务串行
RIMS 实例 · 任务卡「任务 #47：实现 BlobSasService。范围：签发 ≤15min SAS + 路径前缀校验 + RBAC 检查 + 审计埋点。验收：mvn test -Dtest=BlobSasServiceTest 全绿 + gitleaks 无告警。依赖：#31 KeyVaultService。分支：arena/047-blob-sas」
产出：tasks.md（预计 60~80 个会话级任务）+ 依赖图

会话生成：生成 → 验证 → 修复循环

AI 执行 · 循环自纠
每个任务的执行现场：AI 读宪法 → 探索相关代码 → 出实现计划 → 生成代码 → 自动跑验证命令（mvn test / pnpm lint / type-check / build / flyway info）→ 失败读报错自修复 → 循环直到全绿。验证不过，会话不许结束（Stop hook 门禁）。
  • POC 已验证此节奏：12 天 167 次提交，日均 14 个"生成-验证-合并"循环
  • AI 必须出示证据（测试输出/命令回显），不接受"已完成"的口头断言
RIMS 实例 · 典型循环生成 DynamicQueryBuilder → 跑测试发现 OR 条件未参数化（violates 白名单规则）→ AI 读到 lint 报错 → 自动重构为白名单枚举 + 参数化 → 重跑全绿 → 提交 `feat(query): whitelist-enforced dynamic SQL builder`
产出：全绿的分支 + 测试证据 + 符合 Conventional Commits 的提交

审查合并：人审三类 diff，其余快速过

人审查 · 不可绕过
全绿分支进入人工审查。审查资源聚焦三类 diff，其余（纯页面、纯样式、测试补充）快速扫描合并：
  • 安全敏感：密钥处理、SQL 构造、SAS 签发、脱敏路径 —— 逐行审
  • 不可逆：销毁脚本、DDL 迁移 —— 逐行审 + 第二人复核
  • 跨边界：引擎接口、状态机跳转、宪法文件本身 —— 架构师审
RIMS 实例 · 审查拦截场景AI 生成的销毁服务里，VACUUM 参数写死 RETAIN 0——审查发现后要求改为宪法规定的"先归档清单、后销毁、保留审计快照"，避免物理删除不可追溯。
产出：合并到主干 + 审查记录；人的时间只花在 20% 的高风险 diff 上

验收回放：BDD 重跑 + 度量归档

AI 回放 · 人签字
里程碑与 UAT 不再人工点页面：阶段一的 BDD 用例在准生产环境全量机械回放；同时跑审计演练（脱敏对照查询 / SAS 过期 403 / 越权拒绝 / 审计一键导出）。全绿后人签字验收。
  • 度量归档：AI 生成占比、返工率、缺陷率、任务耗时——为下一个项目校准估算
  • 会话档案归档：167+ 会话记录成为"为什么这么写"的完整追溯材料
RIMS 实例 · UAT 回放清单（节选）① 无脱敏权限账号查 CUSTOMER_ORDER → 断言 customer_name = "张*三"；② SAS URL 16 分钟后访问 → 断言 403；③ 模拟双人销毁缺第二人 → 断言状态仍 EXPIRING；④ 切换 QueryEngine 到 Databricks 实现 → 断言全量 BDD 仍绿。
产出：UAT 签字 + 审计演练报告 + 度量基线（供持续改进）
六步与传统五阶段的对应关系：需求结构化+Spec 冻结 ≈ 传统的"需求+架构设计"（但产物从文档变成可执行规格）；任务拆解+会话生成 ≈ 传统的"编码"（但人从写代码变成管会话）；审查合并+验收回放 ≈ 传统的"测试+交付"（但测试已前置嵌进生成循环）。总人天从 290 降到 159（-45%），重心从编码（150 人天）移到规格（30 人天）——详见第 05 章。

3.1 六步骤的工具化：用 GitHub Spec Kit 跑同一套流程

六步骤不需要自建工具链。GitHub 官方开源的 Spec Kit（github/spec-kit · 129.6k star · MIT · 2026-08 核实）把"先定义要建什么，再动手建"的规格驱动开发（SDD）做成了现成 CLI，与 30+ AI 编码代理兼容（Claude Code / Copilot / Codex / Gemini CLI 等，含本仓库在用的 pi 类工具）。其核心主张：规格不再是写完即弃的脚手架，而是可执行的——直接驱动实现生成。安装两条命令即得与六步骤同构的流水线：

安装与初始化uv tool install specify-cli
specify init rims-decommission --integration copilot  # integration 可换 claude / codex / gemini 等 30+ 代理
Spec Kit 命令干什么对应六步骤在 RIMS 怎么用
/speckit.constitution建立项目治理原则，此后每个生成步骤强制遵守STEP 2把 AGENTS.md 七条 Do NOT + 三条红线 + 分层边界 + 状态机规则写入 constitution.md
/speckit.specify生成需求与用户故事——只写 what/why，不写技术栈STEP 1四条 Epic（登记→同步→查询→销毁）各生成一份 spec.md；验收语句内含
/speckit.clarify可选 · plan 前跑AI 就模糊点反向提问，逼出歧义STEP 1"SAS 有效期几分钟？""销毁需几人确认？""LIMIT 上限多少？"——正补 NFR 量化表
/speckit.plan技术实现计划——这一步才引入技术栈STEP 2引擎抽象（SyncEngine/QueryEngine）、UC 治理、Flyway V19+ 平移策略
/speckit.tasks从 plan 生成可执行任务清单STEP 3生成 60~80 张会话级任务卡；/speckit.taskstoissues 可直接转 GitHub Issues 跟踪
/speckit.analyze可选 · implement 前spec ↔ plan ↔ tasks 跨工件一致性与覆盖率核查护栏 L4规格冻结前跑一遍，防 spec 自相矛盾或任务漏覆盖（官方称之"给英文写的单元测试"）
/speckit.implement按任务清单逐项执行实现STEP 4每个任务在验证循环内跑到全绿（配合第 04 章 Stop hook 门禁）
/speckit.converge★ 存量库专用评估现有代码库与目标 spec 的差距，剩余工作自动转为新任务POC→生产本项目最关键的一条：拿生产 spec 对照 POC 代码库，自动生成"重建任务清单"——Phase B 的工作来源

WHY FIT对 RIMS 的三个加分点

  • converge 匹配 POC 场景：RIMS 是典型的"存量库演进"（Brownfield）——官方三阶段（新建/探索/迭代增强）中明确支持此形态，POC 代码不必推倒，差距自动转任务
  • Presets 支持合规定制：可强制 spec 模板带监管可追溯性、给 plan 加安全审查门——正好承载等保/审计要求
  • Bundles 角色包：PM / 业务分析 / 安全研究员 / 开发者各有一键配置，3.5 人团队按角色取用

BOUNDARY它不覆盖什么（诚实边界）

  • STEP 5 人工审查：三类 diff 强制人审是制度（CODEOWNERS + 分支保护），Spec Kit 不管
  • STEP 6 验收回放：BDD 全量回放需自建测试基建，Spec Kit 只负责到任务执行
  • 七层护栏：jscpd 重复度、gitleaks、ArchUnit 等仍需第 04 章的 CI 配置——工具给流程骨架，护栏要自己立法
采用结论：六步骤中 STEP 1–4 直接用 Spec Kit 命令驱动（不自建流程脚手架），STEP 5–6 与七层护栏由本项目的 CI 制度承接——工具负责流程骨架，制度负责质量底线，两者合起来才是完整的交付轨。第 05 章路线图 Phase A 已将 specify init 纳入首个交付动作。
