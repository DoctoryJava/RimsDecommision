三、为什么不是 A —— 便宜是有代价的

代价一：90% 的数据查不了

  • 每个系统 100 张表，仅 10 张进入数据库
  • 其余 90 张只作文件留存，无法 SQL 检索
  • 监管抽查或跨年回溯，需数人天离线还原
  • 源系统退役后 DDL 与数据字典随之消失，裸文件几年后无人能解释字段含义

代价二：规模天花板

  • Azure PostgreSQL 单实例上限 32 TiB
  • 扣除索引与膨胀，有效热数据仅 15~20 TB
  • 总量约 80 TB 即须分库分表，成本阶梯式上涨

代价三：SSO 触发涨价

  • 对接企业 AD 须升 Enterprise 版
  • 每月固定 ¥1.77 万，与用量无关
  • 3 年 TCO 由 ¥121 万涨至 ¥168 万

代价四：越用越慢，需持续调优

  • 归档数据只增不减，单表破千万行后查询全靠索引支撑
  • 索引须由 DBA 逐系统分析查询模式后手工建立，每接入一个系统重复一次
  • 索引占空间、拖慢写入，且会随时间膨胀，需定期重建；10 TB 级实例维护窗口长达数小时
  • 索引一旦超出内存缓存，响应从毫秒级劣化到秒级甚至分钟级

代价五：定向删除「删不干净」

  • 按时间到期可 DROP PARTITION 秒删；但按个人/按单据的定向删除（个人信息删除权）只能走 DELETE
  • PG 的 DELETE 只标记死元组，明文仍留在数据文件、WAL 与只读副本中
  • 真正回收空间要 VACUUM FULL——全程排他锁、读写全停，并额外占用约 1 倍表大小的磁盘
  • 湖仓侧对应动作是后台重写文件，不锁表、不停服

代价六：15 个系统同生共死

  • 「合一群」意味着共用一个实例，Schema 只隔离权限，不隔离故障与资源
  • 一个系统的大范围检索即可吃满 CPU/IO，拖慢其余 14 个
  • 主从切换虽 < 2 分钟，但误删误改只能走 PITR，恢复窗口最长达 12 小时（Azure 官方口径，随数据量增长）
  • 版本升级、跨 4,096 GiB 扩容等离线操作，一次影响全部系统

代价七：查询前端有硬天花板

  • Appsmith 查询默认 10 秒超时、界面上限 60 秒（自托管可提，但属全局设置）
  • 归档典型诉求恰是跨年份检索与万行级导出，而结果集需整体回传浏览器渲染
  • 页面是逐系统手工拖出来的资产：源表加字段、口径调整都要人工回改 15 套页面
  • 附件与业务数据分属两套存储，无法在同一页面直接预览

代价八：退出成本反而更高

  • 源系统退役后归档层即唯一副本，选型一旦落地极难回头
  • A 的形态（10 张 JOIN 宽表 + 90 张裸文件）已偏离原始库结构，将来迁湖仓需反向拆解
  • Appsmith 页面与权限配置不可移植，换前端等于全部重做
  • 对照：B/B2 为 1:1 原样入湖 + Iceberg 开放格式，换引擎不动数据
关于「代价四」需要特别说明：这是架构差异，不是调优能力问题。
传统数据库靠索引加速——索引要人工设计、占用存储、随数据增长而膨胀，且只对预先设计过的查询有效；业务临时提出新的查询角度，就得重新建索引。
湖仓（B / B2）靠列式存储 + 分区裁剪——按时间自动分区，查哪个月只扫哪个月的数据，无需人工建索引，性能不随总量增长而劣化。
差别在于：A 的查询性能需要持续投入人力维护，B/B2 的性能由架构本身保证。归档系统生命周期长达 5~10 年、数据只增不减，这项差异会逐年放大。
另有两项不单列为卡片、但建议汇报时口头带到。
① 证据效力：A 无法自证「归档数据没被改过」。归档件的价值在于可信留存，而 PG 中的表始终是可写的——任何有写权限的人都能 UPDATE 历史记录，pgaudit 记录的是执行过的语句、不是行的前后值，事后无法比对还原。湖仓侧 Iceberg 以快照方式追加，改动天然留痕、可回溯比对；且 ADLS 容器可开启不可变存储（时间保留策略 + 法务保留），该能力已通过第三方评估、满足 SEC 17a-4、FINRA 4511、CFTC 1.31 的留存要求。
② 再利用价值：A 的归档是「只读留档」，B/B2 的归档是「可用资产」。A 中 90% 的表为裸文件、10% 已被 JOIN 成宽表，将来要做跨系统趋势分析、BI 或模型训练，需要再抽取治理一轮；湖仓的 Parquet/Iceberg 可被任意引擎直接消费，归档数据顺带成为分析底座。
四、B2 的取舍需向上明确
⚠ 一项必须知情的代价：厂商绑定
B2 的数据仍采用 Iceberg 开放格式，但权限、脱敏、审计等治理策略绑定在 Databricks Unity Catalog 上。未来若更换查询引擎，这部分需重新建设。
若公司有明确的「避免厂商锁定」政策，应选 方案 B（Trino），代价是 3 年多付 ¥13 万并自行运维集群。

测算口径：建设 ¥2,500/人天；云资源按 Azure 列表价（未计企业折扣）。若已有 Azure EA 折扣，B/B2 成本还会下降，而A 的 Appsmith 授权费不受云折扣影响。

方案 A

PG 合一群 + AppSmith 低代码

核心栈： 源系统(Oracle/MySQL/DB2 退役) → DataX/SeaTunnel 抽取 → PG 合一群(一主一从·读写分离·PG 原生合规) → AppSmith

  • 存储策略： 100张表，10 张高频关联表入 PG，按 Schema 隔离 + 大表时间分区；一主一从读写分离（主库迁入/销毁、从库承接查询）；剩余 90 张表与附件外置 Azure Blob（Cool→Cold 生命周期分层，SHA-256 台账）。
  • 访问合规： 到期扫描 meta_info → PG DROP PARTITION 秒级删除热存 + Blob 生命周期策略后台异步过期删除冷存文件 → pgaudit 留痕（删除操作本身免费、不占用户算力）。
  • 前端展示： AppSmith 拖拽极速生成查询/报表页面，对实施人员极友好。但需计入商业授权：SSO/SCIM/细粒度 RBAC 属 Enterprise 功能（$2,500/月保底 ≈ ¥1.77 万/月），Business 为 $15/用户·月。
  • 适用场景： 归档系统 10–15 个、数据量 <5TB、要求短期极速上线。
方案 B

湖仓一体 + 自定义配置化平台

核心栈： SeaTunnel → Iceberg 冷湖(全量) → Databricks/Trino 查询 → 定制化开发页面

  • 存储策略： 100 张表全量原样入 ADLS Gen2，Iceberg 管理，介质 ≈¥90~150/TB·月（Azure Blob Hot ¥131 / Cool ¥73 混合，LRS）；冷湖分层 RAW→CURATED→LAKE→SERVE，引擎中立、避免锁定。RAW 层需配套 compaction 与分区设计方能保证查询性能，此为一次性平台能力 + 持续算力开销。
  • 存算分离： 对象存储承载冷湖，Databricks 为独立弹性计算层，按需拉起、按量计费；到期 DROP PARTITION + VACUUM 物理清除。
  • 前端展示： 自定义开发基于元数据的「配置 + 显示」动态查询平台——一次研发，新系统接入零代码、配置即上线。
  • 适用场景： 海量历史系统归档(几十/上百个)、>20TB/PB 级、注重长期成本与横向扩展。
方案 B2 · 读写一体变体

湖仓一体 + Databricks 读写

核心栈： SeaTunnel → Iceberg 冷湖(全量) → Databricks 写 + Databricks SQL 读 → 定制化开发页面

  • 与 B 的唯一差异：查询层由 Trino 换成 Databricks SQL Serverless，写侧、存储、前端完全相同。
  • 换来什么：① UC COLUMN MASK 可用（B 用 Trino 时该能力完全不可用）；② 零集群运维、空闲自动缩到 0；③ 审计与权限单点治理，无需维护 Trino ACL。
  • 代价：治理层绑定 Unity Catalog——数据仍是 Iceberg 开放格式，但权限/掩码/审计策略换引擎需重做，引擎中立性下降。
  • 成本特征：Serverless 按在线时长计费，≤80 TB 比 Trino 常驻更省；120 TB 起因仓库规格上抬反被 Trino 反超（详见成本章）。
  • 前端仍建议自研：虽然 Appsmith 可直连 Databricks，但会导致 UC 列掩码与统一审计双双失效，且 15 系统规模下并不省人天。
为什么单列 B2 而不是直接替换 B：两者架构完全相同，差别只在查询引擎，但这个选择牵动三件事——加密掩码能否用、月费高低、是否绑定厂商，且优劣随数据规模反转，不存在一个放之四海皆准的答案。故并列呈现，由业务规模与合规要求决定。
一句话选型：需要列级脱敏、或不愿养 Trino 集群 → B2；坚持引擎中立、或总存量将超 120 TB → B。

2. 后端 ETL 研发成本 数据同步与清洗工作量 中等 · 混合模式

但"1:1 入湖"≠"入湖即可高性能查询"：RAW 层直出的是大量小文件，Trino 直查会因元数据扫描与 task 调度开销导致响应劣化数倍、算力浪费严重。必须配套周期性 compaction（OPTIMIZE / rewrite_data_files）、分区裁剪设计、ZSTD 压缩与 Z-Order 排序。这部分是一次性平台能力（已含在 B 的 152 Man-day 底座中，新系统接入自动复用），但算力开销是持续的，已按 ¥0.1~0.2 万/月计入月费表。

需先花 1~2 个月研发“动态 JSON 配置化平台”。基建完成后，后续接入新系统零代码开发，配置即可上线。
4. 运维：过期数据删除 生命周期到期后的数据清理 可实现 · 平台托管异步
PG 热存 DROP PARTITION 秒级删除；冷存由 Blob 生命周期管理策略按前缀/标签后台异步过期——删除操作免费、不消耗用户算力、无需自建批删作业。
真实代价不在速度而在确定性与举证：生命周期规则每日评估一次、过期存在最长 24~48h 延迟，"合规要求 T+0 即刻销毁"需另调 Delete API 兜底；且 Cool/Cold/Archive 有 30/90/180 天最短计费期，提前删除照付剩余天数。删除凭证需人工关联 PG 与 Blob 两套日志。 		秒级无感清理 · 单点举证
Iceberg 原生分区，DROP PARTITION 元数据秒级生效 + VACUUM/expire_snapshots 物理清除，无性能抖动。
优势不在"更快"（A 的生命周期同样免费省力），而在销毁动作与查询、审计同处一套元数据——"某条记录已不可查且文件已删"可由一句 SQL 举证；代价是 VACUUM 需消耗计算资源，且同样受 Blob 最短计费期约束。

100 张表全量在湖中，随时可通过 Trino 编写 SQL 直接查询湖内数据，扩展新查询需求无需任何数据搬运。
6. 终端用户查询体验 页面点击查询后的响应速度 两极分化 · 且随数据量劣化
查宽表且命中索引时极快（<500ms）；在 Appsmith 中运行 10 表 JOIN 则极易导致低代码平台 API 超时卡死。
更需关注的是性能随时间劣化：归档数据只增不减，单表破千万行后查询性能完全依赖索引——索引须由 DBA 针对每个系统的查询模式手工设计，新增查询角度就要新建索引；索引本身占用存储、拖慢写入，并随数据膨胀，需定期 REINDEX（10 TB 级实例维护窗口达数小时）。一旦索引超出内存缓存，响应会从毫秒级劣化到秒级甚至分钟级。这是持续的人力投入，而非一次性调优。 		常规延迟 · 依赖治理到位
分布式 MPP 引擎的常规表现，在分区裁剪合理、小文件已合并的前提下首屏通常 2~5 秒，对历史归档属可接受范围。
反之若放任 RAW 层小文件堆积、分区键设计不当，同样的查询可能劣化到数十秒甚至分钟级，并显著推高 DBU/节点开销。B 的性能不是"入湖即得"，而是治理换来的。

9. 数据加密与解密 静态加密、传输加密、密钥管理与查询解密链路 可实现 · 但无引擎级 TDE

隐私数据加解密方案专章

归档系统的加密不是"开个开关"，而是四层叠加：存储层（防磁盘/桶泄露）→ 传输层（防链路窃听）→ 字段层（防 DBA/运维内鬼，这一层才是隐私合规的核心）→ 展示层（防越权查看）。前三层两方案都能做到且差异不大，真正拉开差距的是第三层与密钥管理。本章对 A / B 分别给出可落地的技术选型、代码骨架、密钥轮转策略与合规映射。

一、四层加密模型 · A / B 逐层对照 层级越往下，防护的威胁越"内部"· 第 3 层是隐私合规的分水岭
层级 / 防护目标 方案 A（PG + Blob + Appsmith） 方案 B（Iceberg 湖仓 + Trino/Databricks）
L1 · 存储层静态加密 防：磁盘被拖走、备份文件外泄、云厂商运维接触物理介质 默认开启 · 无需开发
PG 侧：Azure PG 灵活服务器默认 SSE（AES-256，FIPS 140-2），覆盖数据文件、备份、PITR、只读副本；可切换为 CMK（Key Vault / Managed HSM），支持密钥自动轮转。
Blob 冷存：存储账户级 SSE 默认开启，可挂 CMK；另可开启基础设施双重加密。
注：不是 TDE——引擎看到的仍是明文，DBA 一条 SELECT 即得明文。 		默认开启 · 无需开发
ADLS Gen2：账户级 SSE（AES-256）默认开启，可挂 CMK（Key Vault / Managed HSM）+ 基础设施双重加密。
覆盖面：Parquet 数据文件、Iceberg 元数据、附件对象同处一个存储账户，一套密钥策略全覆盖，无需分别配置。
同样是"桶级"防护，防不住有湖仓查询权限的人读明文。
L2 · 传输层加密 防：链路窃听、中间人攻击 成熟 · 强制即可
强制 TLS 1.2+（require_secure_transport=ON）；Appsmith → 后端 API → PG 全链路 TLS；客户端需校验根 CA、主机名与吊销状态。
附件：Blob SAS 走 HTTPS，SAS 令牌设分钟级有效期 + IP 限制。 		成熟 · 强制即可
Trino/Databricks 全链路 TLS；额外需注意 Worker 间 internal communication 也要开 TLS（Trino 默认不加密节点间流量，需显式配置共享密钥 + HTTPS）。
这是 B 比 A 多出的一个易漏配置点。
L3 · 字段级加密 ★ 防：DBA / 运维 / 数据工程师直接查库看到明文——隐私合规真正要求的一层 可实现 · 但有硬伤
路线①：pgcrypto 库内加密 —— 应直接排除
pgp_sym_encrypt(col, key)。密钥随 SQL 明文传入，会出现在 pg_stat_activity、慢查询日志、错误日志与 auto_explain 中——等于把钥匙和保险箱放在一起，且 DBA 本就能看到这些视图，防不住本层要防的人。
路线②：应用层信封加密 —— A 方案下的唯一可行解
密钥永不进入数据库进程，PG 只存密文。核心是两层密钥 + 自描述密文：
KEK（Key Vault 内，只用来加解 DEK，不碰业务数据）
DEK（AES-256-GCM，真正加密字段，被 KEK 包好后存元数据库）
密文自带身份：v1:sys01-2025:base64(nonce|ct|tag)——中间的 DEK 标记让程序一看就知道用哪把钥匙解，这是新旧密钥能长期共存、不停机的根本原因。
启动时一次性把全部 DEK 解到内存（45 把 = 45 次调用），此后百万级加解密全在本地 CPU 完成，不再触碰 Key Vault，避开 429 限流。
需检索的字段另建盲索引列 HMAC-SHA256 截断 8 字节：先命中候选集（走索引），再解密二次过滤碰撞项。
轮换代价可控：KEK 轮换只把 DEK 重新包一次，业务表一行不动、约 14 秒；DEK 按年度分片新建，旧片原地保留——合规上每年换新钥，工程上永不回刷历史（归档数据只增不改，正好受益）。
但代价真实存在：密文膨胀（手机号 5.0×）、盲索引泄露频率、模糊/范围/聚合查询全失效，且版本解析、分片调度、进度台账全是自研代码——详见下方专节。 		原生支持 · 配置化实现
路线①：Iceberg 原生表加密（1.11+）——三级密钥 + Parquet 模块化加密，可列级不同密钥、连 manifest 也加密。但 Trino 只能读不能写，且 v3 支持仍为实验性；B2 用 Databricks 读写，无需走这条。
路线②：aes_encrypt() + UC 列掩码 —— B2 的推荐做法
先分清两件事：UC 列掩码只在查询返回时遮蔽，落盘仍是明文（绕过 UC 直读 Parquet 即得明文）；aes_encrypt 才让落盘为密文。隐私字段须两者组合。
四步落地：① 密钥入 Secret Scope（后端由 Key Vault 撑）；② ETL 写入时 aes_encrypt(col, secret(...))，默认 GCM 每次随机 IV；③ 建掩码函数，内部按 is_account_group_member() 决定调 try_aes_decrypt 还是返回 '***'；④ ALTER TABLE … SET MASK 挂到列上。
为何安全：UC 函数以定义者权限取密钥，而 is_account_group_member() 以调用者身份求值——分析师对 Secret Scope 无权限，自己写 aes_decrypt 也拿不到 key。同一条 SQL，授权者见明文、他人见 ***、直读文件见密文。
三个必守约束：❶ 绝不能改成 ECB（确定性加密会暴露频率分布）；❷ 必须确认业务用户对 Secret Scope 无 READ 权限，否则整套防线归零；❸ 掩码不支持视图，必须打在基表上（另：须先 DROP MASK 再 DROP FUNCTION，顺序反了表会不可访问）。
对比 A 的应用层信封加密：约 2~3 Man-day（A 需 8~12）、轮换只换 Secret 版本、无需盲索引、检索能力全部保留、审计平台原生。代价：掩码策略与审计链路绑定 UC，换引擎需重做（密文本身是标准 AES-GCM，可迁移）。
L4 · 展示层脱敏与解密授权 防：越权用户在页面上看到完整明文 应用层兜底 · 两套体系
后端 API 按角色决定"解密后返回"还是"返回掩码"（138****6666）；或建脱敏视图 CASE WHEN role='admin' THEN decrypt(...) ELSE mask(...) END。
短板：脱敏逻辑写在应用代码或视图里，绕过 API 直连库仍可拿密文/明文；Appsmith RBAC 与 PG RLS 两套策略各自维护，易出现"页面藏了但接口没拦"。 		引擎内生 · 单点治理
Unity Catalog：COLUMN MASK + ROW FILTER 绑定到表，任何引擎、任何路径访问都生效，绕不过去；支持基于 tag 的 ABAC（给列打 PII tag，策略全湖生效）。
Ranger + Trino：column-masking + row-filter 策略同理。
⚠ B 与 B2 在这一层差别巨大：
· B（Trino 读）：UC COLUMN MASK 完全不可用——官方明确「不能通过 Iceberg REST catalog 访问带行过滤/列掩码的表」，凭据代发同样把这类表列入不支持清单。Trino 会直接报错查不到数据（fail closed，不会泄露），需改用 Trino 自身的 rules.json 列掩码或 OPA。
· B2（Databricks 读）：COLUMN MASK 原生可用，绑定在表上，任何路径访问都强制生效。
若列级脱敏是硬需求，这一条基本就决定了必须选 B2。
注意：UC 行列过滤不支持通过 Iceberg REST catalog 访问，混用外部引擎时需验证策略是否仍生效。
L5 · 密钥管理与轮转 防：密钥泄露后无法止损、密钥过期导致数据打不开 需自建轮转链路
L1 的 CMK：Key Vault 自动轮转，PG 自动跟随新版本，零改造。
L3 的字段密钥：需自己设计——密文必须带 key_version 前缀，解密时按版本取对应 DEK；轮转时旧数据可"惰性重加密"（读到旧版本时重写）或批量 UPDATE 重刷。归档场景数据量大、重刷成本高，务必第一版就把版本号设计进去。 		信封加密天然友好
三级密钥结构下，轮转主密钥只需重新包装 KEK，不必重写任何数据文件——这是信封加密相对 A 的字段加密的结构性优势，归档场景（数据只增不改、总量大）收益尤其明显。
Databricks aes_encrypt() 路线同样需自管版本，但可借 Key Vault 密钥版本 + UC 函数封装统一处理。
二、落地实现 · 推荐路线与代码骨架 只给"能直接抄"的方案 · 已剔除有安全硬伤的写法
方案 A · 推荐：应用层加密 + 哈希索引列
  1. 不要用 pgcrypto 在 SQL 里传密钥——密钥会进日志和 pg_stat_activity。
  2. 后端服务启动时用 Managed Identity 从 Key Vault 拉 DEK，缓存在内存（禁止落配置文件）。
  3. 敏感字段入库前加密，密文格式 v{版本}:{base64密文}。
  4. 需精确查询的字段（身份证、手机号）额外存一列 HMAC-SHA256 确定性哈希（带全局盐），索引建在哈希列上。
  5. 解密只在后端 API 内完成，按角色决定返回明文还是掩码。
  6. Appsmith 只调后端 API，绝不直连 PG——否则低代码层会成为绕过解密授权的后门。
-- 表结构：密文 + 确定性哈希双列 CREATE TABLE archive_sys01.customer ( id bigint PRIMARY KEY, name_enc text, -- v1:base64(AES-GCM) idcard_enc text, -- v1:base64(AES-GCM) idcard_hmac bytea, -- HMAC-SHA256(idcard, salt) CONSTRAINT ck_ver CHECK (name_enc LIKE 'v%:%') ); -- 索引建在哈希列，密文列不建索引（建了也用不上） CREATE INDEX idx_idcard_hmac ON archive_sys01.customer(idcard_hmac); -- 精确查询：应用侧先算 HMAC，再等值匹配 SELECT id, name_enc FROM archive_sys01.customer WHERE idcard_hmac = $1; -- $1 = HMAC(用户输入)
务必接受的代价：密文列不能范围查询、不能模糊搜索、不能排序。若业务要求"按姓名模糊搜归档记录"，该字段就不能加密，只能靠 L4 展示层脱敏 + 审计兜底——这是必须提前和业务方确认的取舍。
方案 B · 推荐：Databricks 写侧加密 + UC 列掩码
  1. 写侧（Databricks/Spark）承担加密——因为 Trino 不支持写加密表。
  2. 两种组合，按合规强度二选一：
    ① 强合规：Iceberg 原生表加密（PME 信封加密），连元数据一起加密；
    ② 通用：aes_encrypt() 落密文列 + UC COLUMN MASK 控解密。
  3. 密钥统一放 Azure Key Vault，Databricks 通过 Secret Scope 引用，不落代码。
  4. 用 UC tag（PII）+ ABAC 策略批量生效，避免逐表配置。
  5. 读侧无论 Trino 还是 Databricks，策略都在引擎内强制，绕不过。
-- ① Iceberg 原生表加密（写侧 Spark/Databricks） CREATE TABLE lake.archive.customer (...) USING iceberg TBLPROPERTIES ('encryption.key-id'='<keyvault-master-key>'); -- catalog 侧配置 encryption.kms-type=azure -- ② UC 列掩码：按角色返回明文或掩码 CREATE FUNCTION mask_idcard(v STRING) RETURN CASE WHEN is_account_group_member('pii_reader') THEN v ELSE concat(left(v,3), '***********') END; ALTER TABLE lake.archive.customer ALTER COLUMN idcard SET MASK mask_idcard; -- ③ 基于 tag 的 ABAC：给列打标签即全湖生效 CREATE POLICY mask_all_pii ON CATALOG lake COLUMN MASK mask_idcard TO `account users` EXCEPT `pii_reader` MATCH COLUMNS (has_tag_value('pii','idcard')) AS m ON COLUMN m;
选型提示（按读侧引擎分流）：
· B（Trino 读）：UC 掩码不可用 → 只能走 ETL 侧预脱敏（Databricks 写入时落 xxx_masked 与 xxx_enc 两列，Trino 侧靠表/视图权限决定给谁看哪张）。这条路不依赖任何引擎特性，最稳妥。
· B2（Databricks 读）：可直接用 ② aes_encrypt + UC COLUMN MASK，一处定义全局生效，无需维护双列。
· 两者都不建议走 ① Iceberg 原生 PME：Trino 只读不写、v3 支持实验性，会把写链路锁死。
二之补充 · 路线②（应用层信封加密）到底怎么做、代价在哪 A 方案下的唯一可行解 · 但不等于理想解

先明确一点：路线② 是「A 方案约束下的最优」，不是「所有方案里的最优」。 它之所以成立，是因为 PostgreSQL 引擎本身不具备字段级加密能力（无 TDE、无原生列掩码），只能把加解密整体外移到应用层。代价是数据库退化为纯密文仓库——SQL 的检索能力在这些列上几乎全部失效。

① 三级密钥：为什么必须是「信封」，不能直接调 Key Vault
层级存放位置 / 生命周期作用
主密钥 KEKRSA-2048 / 4096 Key Vault 内，永不导出。可选 Managed HSM（FIPS 140-2 Level 3）。轮换由 KV 托管。 只做 wrapKey / unwrapKey 两个操作，不接触业务数据
数据密钥 DEKAES-256 以密文形态存元数据库；后端启动时 unwrap 一次，仅驻留进程内存，设 TTL 定期刷新 真正加解密业务字段。建议按系统 / 按年度分片，一把 DEK 泄露不波及全量
盲索引密钥HMAC key 必须与 DEK 分开保管，独立轮换 生成可检索的确定性哈希。与 DEK 同源会让攻击者一把通吃
⚠ 为什么不能「每条记录调一次 Key Vault 解密」——这是最常见的实现事故。
Key Vault 的 RSA-2048 操作上限是 2,000 次 / 10 秒 / 每保管库（≈200 次/秒），且是整个保管库共享的配额。 若按行调用：一次返回 1 万行的归档查询 = 1 万次 KV 调用 = 理论耗时 ≥ 50 秒且必然触发 429 限流，同时把同一保管库上其他服务一起拖垮。
信封加密的意义就在这里：全程只调 1 次 unwrap（约 50~200 ms）拿到 DEK，其余全部在本地做 AES-GCM——1 万行本地解密约 20 ms。两者差三个数量级。
② 加密算法与字段设计的四个硬性要求
  • 必须用 AEAD（AES-256-GCM），不能用 AES-CBC 裸模式——后者无完整性校验，攻击者可翻转密文位而不被发现。
  • Nonce 必须每条随机且不重复。GCM 下 nonce 复用会直接泄露明文异或值并使认证失效，这是 GCM 最致命的误用。
  • 密文列存版本前缀（如 v1:base64(nonce|ct|tag)）。没有版本号，将来轮换密钥时无法区分新旧密文，只能停机全量重刷。
  • 加密前先归一化（去空格、统一大小写 / 全半角）。否则「张三」和「张三 」会产生两个不同的盲索引，查不到。
③ 代价一：存储膨胀（短字段尤其明显）
字段明文AES-GCM + base64 后膨胀倍数
手机号（11 位）11 B55 B5.0×
姓名（3 汉字）9 B55 B6.1×
身份证（18 位）18 B67 B3.7×
地址（30 汉字）90 B163 B1.8×

固定开销 = 12 B nonce + 16 B tag + base64 膨胀 1.33× + 版本前缀。字段越短，膨胀比越夸张。再加上每个盲索引列（截断 8 B 存 12 B）及其 B-tree 索引——20 TB 中若 5% 为加密短字段，PG 热存约多占 2.4 TB，每月多付 ¥720~1,080。这笔钱在 A 的 PG 上是贵价 SSD。

④ 代价二：盲索引本身会泄露信息，且只能做等值匹配

密文列无法检索，要支持「按身份证查」就必须额外建 HMAC-SHA256(盐, 明文) 的盲索引列。但这带来两个必须向上说明的问题：

  • 频率分析泄露：HMAC 是确定性的，相同明文恒等于相同哈希。攻击者虽拿不到明文，却能看出哪些行的值相同、各值出现多少次。对低基数字段（性别、婚姻状况、疾病标记）几乎等同于明文——按频次排序即可猜出。
    缓解：只对高基数字段建盲索引（身份证、手机号），低基数字段不建；或截断哈希制造碰撞（如留 8~16 bit），以少量误报换取模糊性，再由后端解密后二次过滤。
  • 能力仍然残缺：盲索引只解决精确等值。LIKE '%张%' 前缀模糊、BETWEEN 范围、ORDER BY 排序、GROUP BY 聚合——在加密列上一律不可用。若业务要按姓名模糊查，只能拆多个前缀盲索引，而索引越多泄露越多。
⑤ 密钥轮换：能做到，但三层的代价差几个数量级
先澄清一个常见误解：业务字段的加解密用的是同一把钥匙，不是「A 加密、B 解密」。
「加密用 A、解密用 B」是非对称模型。在信封加密里，非对称只存在于最外层的 KEK（公钥 wrap、私钥 unwrap）；业务字段本身走对称 AES-256-GCM，同一把 DEK 既加密也解密。
为什么业务字段不直接用 RSA？两个硬限制：① RSA-2048 + OAEP 单次最多加密 190 字节，一个地址字段就可能超；② RSA 解密约 1,000 次/秒，AES-GCM 约 1 GB/秒，差约六个数量级。所以所有成熟方案（TLS、PGP、Signal）都是「非对称包对称」。

② DEK 按「系统 × 年度」分片：sys01-2024、sys01-2025…… 每年新建一把，旧分片原地不动。这样既满足「定期换新钥」的合规要求，又永远不需要回头重刷历史数据——归档数据只增不改，这个特性正好帮了忙。
③ 盲索引密钥设计为不轮换，除非确认泄露。它必须与 DEK 分开保管、分开定义生命周期，绝不能跟着 DEK 一起换。
④ 真正需要「全量重刷」的只有一种情况：密钥确认泄露。这时代价是数天~数周的分批重刷——所以要在设计期就把 DEK 拆细（按系统、按年），把爆炸半径限制住，而不是全局一把钥匙。
⚠ 但这套机制全部要你自己实现——这正是路线② 的隐性成本。
版本前缀解析、KEK 版本 URI 记录、DEK 分片调度、新旧密钥并存期的双读逻辑、轮换失败的回滚、以及「哪些行还没重刷完」的进度台账——Azure PostgreSQL 一样都不提供，全是后端代码。
对照 B2：Unity Catalog 的列掩码策略不涉及密钥轮换问题（掩码在查询返回时施加，底层始终是明文列 + 访问控制）；若确需字段级加密，Databricks 的 aes_encrypt() 配合 Secret Scope 也只需换 Secret 版本，没有盲索引这一层要维护。
⑥ 那么路线② 是不是「最好的方式」？—— 分两层回答。
在 A 方案（PG + Appsmith）的约束内：是，而且没有第二个选项。pgcrypto 有密钥泄露硬伤；Azure PostgreSQL 无 TDE、无原生列掩码；商业插件（如 EDB、CipherTrust）要额外许可且加深绑定。应用层信封加密是唯一既满足《个保法》「去标识化」、又不把密钥交给数据库的做法。

等保 2.0 三级
要求"重要数据在存储和传输过程中的保密性"。
A：L1+L2 满足传输与存储；但"个人信息访问需授权且可追溯"依赖应用层实现，测评时需额外举证 API 侧逻辑。
B：策略在引擎内、审计落 Iceberg 表，举证材料天然齐备。
个人信息保护法
第 51 条要求采取"加密、去标识化"等措施。
关键：SSE/CMK 属于存储加密，不构成"去标识化"——监管关注的是"内部人员能否看到明文"。
两方案都必须做 L3 字段级加密或 L4 强制脱敏，只做 L1 无法满足。
GDPR 被遗忘权
归档场景的高频难题：数据已沉到冷存，如何"删除某个自然人"？
推荐解法（两方案通用）：Crypto-Shredding——按数据主体分配独立 DEK，需要"删除"时直接销毁该主体的 DEK，密文即成永久不可读，无需物理重写 PB 级文件。
这是归档架构里性价比最高的合规设计，建议第一版就纳入。
最易踩的三个坑
① 误以为 Azure PG 有 TDE——没有，只有存储级 SSE；
② 用 pgcrypto 在 SQL 里传密钥——密钥进日志，等于没加密；
③ 忘了 Trino 节点间通信默认不加密——B 方案需显式开启 internal TLS。
加解密维度的选型结论
若隐私合规是硬约束，这一维度 B 明显占优，理由有三：
① 解密授权的强制力不同——A 的脱敏逻辑在应用层，任何绕过 API 的路径（DBA 直连、报表工具直连）都失效；B 的列掩码/行过滤绑定在引擎元数据上，换任何客户端都绕不过。
② 密钥轮转成本不同——A 的字段加密轮转需重刷存量数据，归档场景动辄数十 TB；B 的信封加密只需重新包装 KEK，数据文件一个字节都不用动。
③ 加密粒度不同——B 可做到连列名、分区边界、统计值都是密文；A 的 PG 侧元数据始终明文。
但要清醒：B 的这些能力不是开箱即用。Trino 不支持写加密表、UC 行列过滤不兼容 Iceberg REST catalog、Ranger/UC 策略建模本身就是数人天的工作量。前期投入已计入 B 的 152 Man-day 底座；若归档数据不含敏感个人信息，这部分能力属于过度设计，A 的 L1+L2+应用层脱敏足够。

归档系统的权限本质上只需回答两个问题：①「谁能进哪个系统的哪个页面」②「谁能查哪张表」。

· L1 系统/页面级——用户登录后能看到哪几个已归档系统、每个系统里的哪些页面（查询页/报表页/附件页）

· 附件访问授权（按表/系统粒度）
✗ 明确排除

⚠ 关于 Appsmith 授权档位的常见误解
常被误认为「SSO / SCIM / 细粒度 RBAC 均需 Enterprise」，但细粒度 RBAC 并不在其中。据 Appsmith 官方定价页：「自定义角色与访问控制（Custom roles and access controls）」属于 Business 档（$15/用户·月）就有的功能，Enterprise 独有的是 SAML/OIDC SSO、SCIM 用户同步、CI/CD、私有嵌入。
对本章的影响：既然不需要行列级权限，页面级 RBAC 在 Business 档即可完全满足。是否上 Enterprise，唯一的决定因素变成「要不要对接企业 AD/SSO 单点登录」，而不再是权限粒度。若贵司接受 Appsmith 独立账号体系（或用 Google SSO），A 方案可稳稳停在 Business 档，月费按 30~60 用户计约 ¥0.32~0.64 万/月，而非 Enterprise 的 ¥1.77 万/月。

归档数据的访问诉求几乎都是"我原来那个系统的数据，我还要能查"。按系统切分，角色数量 = 系统数，线性可控、职责清晰；按敏感度切分则需要行列级支撑——而这正是本次排除的范围。
auditor 角色是关键分歧点
A：审计员虽有全部 Schema 的 SELECT，但只能逐个系统页面分别查——A 无冷查询层，跨系统关联需人工导出比对。
B：一条 SQL 跨 15 个系统 JOIN 检索。若审计/监管抽查是刚需，这一条足以定选型。
角色数量估算
15 个系统 → 15 + 3 = 18 个角色。
A：Appsmith 里建 18 个自定义角色 + PG 里建 18 个对应 role，两边手工对齐。
B：IdP 里建 18 个组，前端与 Trino/UC 共用同一套组名，只需一处维护。
三、落地配置骨架 可直接套用 · 均为「系统/页面级 + 表级」两层，无行列级配置
方案 A · Appsmith RBAC + PG Schema 授权
  1. 页面级：每个归档系统建一个 App，把 App 授权给对应角色（Business 档自定义角色即可）。
  2. 表级：PG 按 Schema 批量授权，与"每系统一 Schema"的设计天然对齐。
  3. 关键：Appsmith 数据源必须为每个角色配独立的 PG 连接账号，否则所有页面共用一个高权限连接，表级权限形同虚设。
  4. 兜底：REVOKE 掉 PUBLIC 的默认权限，避免新建表被意外可见。
-- 1) 每系统一个只读角色 CREATE ROLE role_sys01 NOLOGIN; GRANT USAGE ON SCHEMA archive_sys01 TO role_sys01; GRANT SELECT ON ALL TABLES IN SCHEMA archive_sys01 TO role_sys01; -- 未来新建的表自动继承（关键，否则新表默认不可见） ALTER DEFAULT PRIVILEGES IN SCHEMA archive_sys01 GRANT SELECT ON TABLES TO role_sys01; -- 2) 收回 PUBLIC 默认权限（安全兜底） REVOKE ALL ON SCHEMA archive_sys01 FROM PUBLIC; -- 3) 审计员：一次性授予全部系统只读 CREATE ROLE role_auditor NOLOGIN; -- 对每个 schema 循环执行 GRANT（可用 DO 块批量） DO $$ DECLARE s text; BEGIN FOR s IN SELECT nspname FROM pg_namespace WHERE nspname LIKE 'archive_%' LOOP EXECUTE format('GRANT USAGE ON SCHEMA %I TO role_auditor', s); EXECUTE format('GRANT SELECT ON ALL TABLES IN SCHEMA %I TO role_auditor', s); END LOOP; END $$;
最易踩的坑：Appsmith 里若所有 App 共用一个数据源（同一个 PG 账号），PG 的表级权限完全不起作用——因为数据库看到的永远是同一个高权限用户。必须按角色拆分数据源连接，这是 A 方案表级权限能否真正生效的前提。
方案 B · JSON schema 页面控制 + 引擎表级授权
  1. 页面级：页面配置里声明 visibleRoles，前端渲染前过滤。
  2. 必须：后端 API 二次校验，前端隐藏只是体验优化，不是安全边界。
  3. 表级：查询侧以 Trino 为主则用 rules.json；以 Databricks 为主则用 UC GRANT（推荐，可继承）。
  4. 组名统一：IdP 组名 = 前端角色名 = Trino group = UC group，避免三处各写一套。
// 1) 页面配置（元数据驱动前端） { "pageId": "sys01_query", "title": "01号系统 · 归档查询", "visibleRoles": ["sys01_viewer", "auditor"], "dataset": "lake.sys01.orders" } -- 2a) Trino 文件式访问控制 rules.json（无需 Ranger） { "catalogs": [ {"group":"sys01_viewer|auditor", "catalog":"lake", "allow":"read-only"} ], "tables": [ {"group":"sys01_viewer", "catalog":"lake", "schema":"sys01", "privileges":["SELECT"]}, {"group":"auditor", "catalog":"lake", "schema":".*", "privileges":["SELECT"]}, // 兜底拒绝：不写则默认 deny，但显式更稳妥 {"catalog":".*", "schema":".*", "privileges":[]} ] } -- 2b) Unity Catalog（权限自动向下继承） GRANT USE CATALOG ON CATALOG lake TO `sys01_viewer`; GRANT USE SCHEMA, SELECT ON SCHEMA lake.sys01 TO `sys01_viewer`; -- 现有+未来的表全覆盖
Trino 配置注意：其访问控制不做层级下钻推导——catalog / schema / table 三级都要显式配，任何一级漏配即默认拒绝，这是社区里最常见的踩坑点。相比之下 UC 的 GRANT 支持向下继承，维护量明显更小。
四、权限校验链路 · 关键看「哪一道是真正的闸门」 绿色 = 强制生效的安全边界 · 灰色 = 仅体验优化，可被绕过
共同结论：真闸门都在数据层
三个方案最终生效的权限边界都是「表级授权」——A 在 PG，B 在 Trino rules.json，B2 在 UC GRANT。页面级控制在两边都只是体验层，都可被直连绕过。所以表级授权必须配全，不能依赖前端隐藏。
A 的独有风险
Appsmith 数据源连接的账号权限是 A 的阿喀琉斯之踵。若图省事全用一个 postgres 超级账号，PG 那层 GRANT 写得再细也形同虚设。这是实施时最容易埋雷、且审计时最容易被抓的点。
B 的独有风险
后端 API 二次校验需要自研且必须覆盖全部接口——漏写一个接口就是一个越权漏洞。A 因为走 Appsmith 内建机制，反而不存在"漏写"的可能。这是 B 在本章范围内被 A 扳回的一分。
两边都别忘的兜底
① PG 侧 REVOKE PUBLIC；② ALTER DEFAULT PRIVILEGES 让新表自动继承权限；③ Trino 显式写兜底 deny 规则；④ 定期跑权限巡检脚本比对实际授权与设计基线。
五、结论 · 收敛范围后的重新评估 与上文表格第 13 项的原结论对比
原结论需要修正：「B 单点治理全域一套」的优势被大幅削弱
上文表格第 13 项给 B 的评价是「可实现 · 单点治理 · 全域一套」，但那个判断建立在行级过滤、列级掩码、基于标签的 ABAC 这些能力上。你已明确排除这三项——B 的加分项基本被移除了。

在「仅系统/页面级 + 表级」的范围内，两个方案是这样的：
· A 反而更省事：Appsmith 的 App/Page 授权是纯配置、零代码，PG 的 Schema 级 GRANT 是几十年成熟的标准 SQL，两者都不需要额外组件。而且 Business 档（$15/用户）就够——不必为权限上 Enterprise。
· B 需要自研两块：OIDC 登录对接 + 后端 API 鉴权校验。虽已含在 152 Man-day 底座里，但这个范围内 B 拿不到与投入相称的收益——它擅长的精细治理你不需要。

B 在本章范围内仍保有的两项实质优势：
① 审计溯源一步到位——Trino/Databricks 原生记录"谁 + 什么 SQL + 访问了哪些对象"，A 需人工关联 Appsmith 日志与 pgaudit 两套体系；
② auditor 角色的跨系统检索——A 无冷查询层，审计员即便有全部 Schema 权限也只能逐系统查。

B 与 B2 在权限维度的差别：B2 用 UC GRANT（权限自动向下继承、审计有 system.access.audit 开箱即用），B 用 Trino rules.json（三级显式配置、审计需自建 Event Listener）。纯表级权限场景下 B2 的配置与维护量约为 B 的一半，代价是治理层绑定 UC。

选型建议：如果权限需求确实止步于"系统/页面 + 表"这两层，那么权限维度不再构成选 B 的理由，A 在这一维度甚至略优（配置化、无自研、Business 档即可）。此时决策应回到前几章的数据规模、冷数据是否需要 SQL 检索、跨系统审计是否刚需三个问题上。

方案 B 应用架构的要点：查询与写入分离。
写入链路（SeaTunnel → Databricks ETL → Iceberg）与查询链路（查询代理 → Trino → Iceberg）解耦，存算分离、各自弹性扩缩。相比 B2 把查询也交给 Databricks Serverless，B 的读侧由自建 Trino 承担，保持引擎中立、不被单一厂商绑定，但需自行运维 Trino 集群、维护 rules.json 授权，且无法使用 UC 列级脱敏。应用层的六个后端服务、前端平台、元数据库与存储在 B / B2 之间完全一致。
⚠ 方案 B 落地需注意：
① Trino 集群需自建运维（搭建、升级、扩缩容、调优）——需专职大数据运维，这是相对 B2 的主要增量成本。
② 查询代理到 Trino 的连接须走私有链路，Trino 节点间通信默认不加密，需显式开启 TLS。
③ 权限需两处维护：Databricks/UC 管写侧，Trino rules.json 管读侧——catalog/schema/table 三级都要显式配置，漏配即拒绝。
④ 附件与业务数据分账户存放，附件读取走后端流式代理（非 SAS 直连），实现鉴权、审计与防越权。
